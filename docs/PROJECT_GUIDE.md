# Проект STM32F407VG LAN v1

## Назначение
Файл сопровождения проекта описывает структуру, инструменты и шаги настройки, чтобы можно было открыть проект на другом компьютере без дополнительных вопросов.

## Содержимое проекта

- `stm32f407vg_lan_v1.ioc` — проект STM32CubeMX с конфигурацией МК и периферии.
- `.mxproject` — внутренний файл CubeMX для настройки генерации.
- `f407.sch` — схема платы в Autodesk Eagle.
- `EWARM/` — артефакты генерации IAR Embedded Workbench (EWARM), которые можно игнорировать, если вы не используете IAR.
- `Core/Inc/`, `Core/Src/` — пользовательский и сгенерированный код.
- `Drivers/` — STM32Cube HAL и CMSIS, необходимые для сборки.

## Окружение и инструменты

- STM32CubeMX 6.17.0 compatible
- STM32CubeF4 FW package V1.28.3
- ST-Link V2 или другой программатор, поддерживающий STM32F4
- Опционально: Autodesk Eagle для открытия `f407.sch`
- VS Code — основная среда редактирования

## VS Code

- В этом проекте `VS Code` используется как основной редактор исходников.
- Файлы CubeMX и исходники находятся в проекте, а `EWARM/` может оставаться в папке как сгенерированный артефакт.
- Сборка выполняется внешней цепочкой инструментов: `arm-none-eabi-gcc`, `make`, `CMake`, STM32CubeMX или другая система сборки.
- Программирование платы выполняется через `ST-Link V2` (клон) с помощью `STM32CubeProgrammer`, `OpenOCD`, `st-flash` или аналогичного инструмента.
- Если хотите, добавьте в `VS Code` задачи `tasks.json` для вызова сборки и прошивки.

- Тактовая частота APB2: 80 MHz

- `USART1` на PA9 (TX) / PA10 (RX), асинхронный режим, 921600 baud
- `USART3` на PD8 (TX) / PD9 (RX), асинхронный режим, 921600 baud
- `SWD` на PA13 / PA14
- `HSE` на PH0/PH1
- GPIO выходы для индикаторов:
  - PB4 = LED7
  - PB5 = LED8
  - PD0 = LED3
  - PD1 = LED4
  - PD4 = LED5
  - PD7 = LED6

## Важные примечания по открытию на другом компьютере

1. Скопируйте весь каталог проекта целиком, чтобы относительные пути сохранились. Проект использует относительные пути к `Core/`, `Drivers/` и `EWARM/`.
2. Откройте `stm32f407vg_lan_v1.ioc` в STM32CubeMX. Если пакет STM32CubeF4 V1.28.3 не установлен, установите его через менеджер пакетов CubeMX.
3. В генераторе CubeMX проверьте:
   - `Project Manager -> Project Name` = `stm32f407vg_lan_v1`
   - `Project Manager -> Keep User Code` = включено
   - `Project Manager -> Copy only the necessary libraries` = включено (или `Library copy = 1`)
4. Если вы используете собственную сборку, настройте параметры генерации так, чтобы получать только `Core/` и `Drivers/`, а не файлы IAR.
5. Если CubeMX пересобирает проект, любые изменения в `Core/Src/main.c` и `Core/Inc/main.h` должны сохраняться внутри специальных блоков `/* USER CODE BEGIN */` / `/* USER CODE END */`.

## КРИТИЧНО: startup_stm32f407xx.s должен содержать `.weak` для каждого обработчика

`Core/Startup/startup_stm32f407xx.s` — **не штатная генерация CubeMX** (CubeMX в этом проекте генерирует startup только для IAR, `EWARM/startup_stm32f407xx.s`). Файл для GCC/CMake был написан вручную при настройке CMake-сборки.

**Один раз уже была серьёзная ошибка:** в файле отсутствовали все директивы `.weak` перед строками вида `.thumb_set ИмяHandler, Default_Handler`. Без `.weak` эти имена (`SysTick_Handler` и вообще все ~80 обработчиков прерываний) становятся локальными алиасами на `Default_Handler` *внутри самого startup-файла*, и таблица векторов прерываний (`__isr_vector`) навсегда зашивает адрес `Default_Handler` — даже если в `Core/Src/stm32f4xx_it.c` есть нормальная реализация (например, `SysTick_Handler` с `HAL_IncTick()`). Компилятор и линковщик **не выдают ни одной ошибки/предупреждения** — всё линкуется "чисто".

Симптом был коварный: код без прерываний (GPIO, инициализация UART) работал нормально, прошивка успешно писалась и проверялась. Но как только код стал зависеть от прерывания (`HAL_Delay()` через `SysTick`), ядро намертво вешалось в `Default_Handler` (бесконечный `b .`) при первом срабатывании SysTick — `HAL_Delay()` никогда не возвращался. Внешне выглядело как "LED не мигают" / "зажглись и зависли".

**Если когда-нибудь снова придётся пересоздавать/чинить `startup_stm32f407xx.s` вручную:**
- Перед каждой строкой `.thumb_set XXX_Handler, Default_Handler` обязательно должна идти `.weak XXX_Handler`.
- Лучше вообще не писать этот файл руками — взять готовый `startup_stm32f4*.s` из пакета `STM32CubeF4` (`Drivers/CMSIS/Device/ST/STM32F4xx/Source/Templates/gcc/`) и подставить под нужный МК.
- Чтобы проверить, что баг не вернулся: halt ядро через OpenOCD дважды с разницей в пару секунд и командой `resume` между ними, прочитать `pc` и память по адресу глобальной переменной `uwTick` (см. `arm-none-eabi-nm build/*.elf | grep uwTick` для адреса) — если значения не меняются между чтениями, обработчики прерываний не работают.

## Прошивка через OpenOCD — известные проблемы и готовое решение

Эти грабли уже пройдены один раз (см. историю отладки) — **не наступайте на них снова**, просто используйте задачу `Flash STM32F407VG` из `.vscode/tasks.json`, она уже всё учитывает.

### Особенности этой платы (custom, `f407.sch`)

- **NRST от ST-Link к плате не подключён.** Аппаратный reset через `connect_assert_srst` недоступен.
- **BOOT0 (вывод 94 МК, U1) не выведен на джампер/разъём** — подтянут к GND резистором `R4` (10 кОм), и больше никуда. Чтобы временно поднять BOOT0 в "1" (например, для входа в системный bootloader), нужно физически припаивать временный провод на вывод 94 или на верхний контакт R4 — штатного способа нет.
- Напряжение на target обычно **~3.12–3.15 В** — на нижней границе нормы, но рабочее. Если когда-нибудь снова появится `init mode failed (unable to connect to the target)`:
  1. Это почти всегда обрыв/контакт SWDIO/SWCLK/GND, а не прошивка.
  2. Без NRST помогает приём "поймать момент после подачи питания": обесточить плату, в PowerShell крутить `openocd ... -c init -c halt` в цикле и включить питание во время цикла.

### Баг команды `program ... verify` в текущей сборке OpenOCD

Используемая сборка — `xPack OpenOCD 0.12.0+dev-02228-ge5888bda3-dirty`. На этой плате команда-шорткат
```
program build/stm32f407vg_lan_v1.bin verify reset exit
```
**стабильно проваливает верификацию** (`Error: checksum mismatch - attempting binary compare` → `Verify Failed`), даже когда запись реально проходит корректно. Перед ошибкой в логе всегда видно аномалию:
```
Info : flash size = 512 bytes
Warn : no flash bank found for address 0x00000000
```
— это внутренний баг авто-определения банка флеша именно в обёртке `program`, не реальная проблема платы/питания/прошивки (проверено: `RDP`/`WRP` отключены, `flash info 0` показывает все 12 секторов "not protected", напряжение в норме).

**Решение (уже встроено в задачу `Flash STM32F407VG`):** не использовать `program`, а делать запись и верификацию явными командами:
```
init
reset halt
stm32f4x mass_erase 0
flash write_image build/stm32f407vg_lan_v1.bin 0x08000000
verify_image build/stm32f407vg_lan_v1.bin 0x08000000
reset run
```
Это работает надёжно и подтверждено побайтовой верификацией — проверено и на пониженной (200/125 кГц), и на штатной (2000/1800 кГц) скорости SWD, оба раза успешно.

Скорость SWD **не ограничивается специально** — используется штатная из `target/stm32f4x.cfg` (~1.8 МГц). Разгон до 8 МГц, который встроен в хук `reset-init` этого конфига, в данной последовательности не задействуется, потому что используется `reset halt`, а не `reset init` (хук `reset-init` срабатывает только на `reset init`) — поэтому повторно разгонять/тормозить скорость вручную не требуется. Если в будущем кто-то добавит `reset init` в цепочку и вернётся проблема — сначала проверьте, не ожило ли воздействие этого хука, и при необходимости верните принудительное ограничение скорости (`adapter speed 200` + переопределение хуков `reset-init`/`reset-start`), это уже проверенный fallback.

## ТЕКУЩАЯ ОТЛАДКА: обрыв TCP-связи под нагрузкой (статус на 2026-06-18, не завершено)

**Симптом:** при отправке нескольких сообщений в UART1 модуля (которые форвардятся в TCP) подряд связь стабильно умирает после определённого количества пакетов, требуя ресета. Без аппаратного ресета модуль не виден в сети (ARP не отвечает) с ПК.

### Подтверждённые и исправленные баги (уже в коде, проверено сборкой)

1. **`HardFault_Handler` был "тихим" `while(1)`** (`Core/Src/stm32f4xx_it.c`) — если бы случился реальный HardFault, диагностировать было бы невозможно. Исправлено: теперь печатает `[HARDFAULT] PC=... LR=...` в UART1 перед остановкой (через ассемблерный трамплин + `HardFault_C_Handler`). **На практике HardFault не наблюдался** ни разу — значит, дело не в crash/segfault уровня CPU.

2. **`ethernetif_reset()` добавлена** (`Core/Src/ethernetif.c`) — функция полного пересоздания ETH: `HAL_ETH_Stop_IT` → `HAL_ETH_DeInit` → аппаратный сброс через RCC (`__HAL_RCC_ETHMAC_FORCE_RESET/RELEASE_RESET`, т.к. `HAL_ETH_DeInit` НЕ дёргает линию аппаратного сброса) → `low_level_init()` (полная переинициализация MAC/DMA/PHY заново, включая NRST PHY). Вызывается из `tcp_echo_client.c`/`on_err()` после `ETH_RESET_AFTER_FAILS=3` неудачных попыток подключения подряд (~15 сек). **Подтверждено рабочим**: после такого сброса IP/PHY/ARP восстанавливаются (видно `[lwip] IP: 10.0.1.60` и реально устанавливается TCP-соединение).

3. **`HAL_ETH_Init()`/`DeInit()` не очищают `EthHandle.TxDescList`/`RxDescList`** — проверено по исходникам HAL (`Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_eth.c`), там просто нет кода, который бы их обнулял. Из-за этого счётчик занятых TX-буферов (`BuffersInUse`) копился через рестарт ETH и никогда не возвращался к 0. Исправлено: в `ethernetif_reset()` добавлен явный `memset(&EthHandle.TxDescList, 0, ...)` / `RxDescList`. **Подтверждено в логе**: после фикса `txbuf=0` сразу после `[eth] resetting ETH peripheral`, раньше оставалось зависшим на старом значении.

4. **Double-free pbuf при таймауте передачи** (`low_level_output()` в `ethernetif.c`) — при таймауте `HAL_ETH_Transmit()` (20 мс) HAL сам форсированно очищает бит OWN дескриптора (`heth->ErrorCode |= HAL_ETH_ERROR_TIMEOUT`), и pbuf будет освобождён позже через `HAL_ETH_ReleaseTxPacket()` → `HAL_ETH_TxFreeCallback()`. Старый код ДОПОЛНИТЕЛЬНО делал `pbuf_free(p)` сразу при любой ошибке — двойной free на один pbuf при таймауте, что портит heap lwIP. Исправлено: `pbuf_free(p)` теперь вызывается только если `EthHandle.ErrorCode` НЕ содержит `HAL_ETH_ERROR_TIMEOUT` (т.е. дескриптор не был поставлен в очередь и никто другой его не освободит).

5. **`ETH_TX_DESC_CNT`/`ETH_RX_DESC_CNT` увеличены с 4 (умолчание HAL) до 8** (`Core/Inc/stm32f4xx_hal_conf.h`, override перед `#include "stm32f4xx_hal_eth.h"`) — диагностический шаг, не финальное решение.

6. В `[alive]` heartbeat (`main.c`) добавлено поле `txbuf=%lu` = `EthHandle.TxDescList.BuffersInUse` для прямого наблюдения за утечкой TX-дескрипторов без доп. инструментирования.

### РЕШЕНО (2026-06-18): главная причина найдена и подтверждена инструментацией

Гипотеза из предыдущей версии этого раздела **подтверждена напрямую**: добавлен временный debug-print вокруг `HAL_ETH_ReleaseTxPacket()` (сравнение `BuffersInUse` до/после) и при `tcp_write()==ERR_MEM`. Лог показал:

- `[eth] release stuck: before=N after=N` — печаталось **на КАЖДОМ вызове, начиная с before=1** (то есть с первой же передачи после `[lwip] IP: ...`). `HAL_ETH_ReleaseTxPacket()` не освободил ни одного дескриптора ни разу за весь сеанс (>100 передач).
- `BuffersInUse` рос линейно до 104 и затем заморозился — ровно в этот момент начались `[tcp_echo] tcp_write ERR_MEM (heap exhausted?)`, подряд и постоянно. Это подтверждает: куча lwIP (`MEM_SIZE=16KB`) действительно исчерпывается накопленными pbuf, которые никогда не освобождаются через `HAL_ETH_TxFreeCallback()`.

**Корневая причина:** голова FIFO-очереди дескрипторов (`TxDescList.releaseIndex`, который никогда не сдвигается с 0) застряла с битом OWN навсегда уже на первой передаче — почти наверняка гонка сразу после `HAL_ETH_Start_IT()` в `low_level_init()` (первая передача, скорее всего DHCP DISCOVER, ставится в дескриптор раньше, чем DMA/MAC реально готовы её обслужить). Поскольку `HAL_ETH_ReleaseTxPacket()` устроен строго по FIFO (см. `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_eth.c:1463` — `while (numOfBuf!=0 && pktTxStatus!=0)`, останавливается на первом дескрипторе с установленным OWN), застрявшая голова блокирует освобождение АБСОЛЮТНО ВСЕХ последующих дескрипторов навечно, даже если они реально передались по проводу (а они передавались — ПК получал данные все 60+ секунд, это видно по живому диалогу в логе).

**Фикс (применён, `Core/Src/ethernetif.c`, `low_level_output()`):** если `BuffersInUse > ETH_TX_DESC_CNT` (что само по себе невозможно при корректной работе кольца — прямое доказательство застревания, а не "просто давно не освобождали"), принудительно очищаем застрявший дескриптор-голову той же командой, что использует сам HAL при таймауте (`DESC0 = ETH_DMATXDESC_FS | ETH_DMATXDESC_LS`, это сбрасывает бит OWN), и сразу повторно вызываем `HAL_ETH_ReleaseTxPacket()`, чтобы реально освободить pbuf через `HAL_ETH_TxFreeCallback()`. Временные debug-print (`release stuck`, `tcp_write ERR_MEM`) убраны после подтверждения диагноза — если поведение вернётся, инструментацию легко восстановить (см. git-историю/предыдущую версию этого файла).

**Обновление после первого теста на плате:** гейт `> ETH_TX_DESC_CNT` почти не помог (рост до 50+ продолжался). Заменён на безусловный дренаж: на каждом вызове `low_level_output()` цикл `while (BuffersInUse > 0 && guard-->0) { force-clear головы; HAL_ETH_ReleaseTxPacket(); если без изменений - break; }` (до `ETH_TX_DESC_CNT+1` итераций). **Второй тест:** утечка стала значительно меньше (плато на ~45 вместо 104, и `txbuf=0` после рабочих ресетов), но не до конца ноль во время самого всплеска сообщений — видимо, дренаж не успевает полностью разгрузиться в рамках одного вызова при быстрой серии, и сообщения заканчиваются раньше, чем цикл успевает дойти до 0 (после остановки потока новых вызовов дренаж тоже не может продолжиться, т.к. он только внутри `low_level_output()`). Это уже не критично — TX-утечка больше не доминирующая причина отказа.

### НОВАЯ ОТКРЫТАЯ ПРОБЛЕМА (вскрылась после починки TX-утечки): module не переподключается после `ethernetif_reset()`

После того как TX-утечка перестала маскировать остальные эффекты, проявился **отдельный** баг: после нескольких циклов `ethernetif_reset()` модуль входит в устойчивый цикл "сброс → `[lwip] IP: ...` → мгновенный `connection error` → через 3 попытки снова сброс", **навсегда**, без единого успешного `[tcp_echo] connected`. При этом `txbuf=0` (утечки дескрипторов больше нет), `eth=LINK_UP` после первого тика — то есть PHY физически поднимается, но TCP не устанавливается.

Важное наблюдение пользователя: ARP-таблица ПК **показывает корректную запись** для модуля (`10.0.1.60 → 02-00-00-00-00-01, dynamic`) даже во время этого зависания — то есть на уровне Ethernet/ARP всё видно нормально, проблема глубже (похоже на TCP handshake или RX-путь модуля).

Аналогия с уже найденным TX-багом: возможно, есть **симметричный баг на RX-стороне** — `g_eth_rx_alloc_status` (бывший `RxAllocStatus`, см. `ethernetif.c`) может зависать в `RX_ALLOC_ERROR` после нескольких циклов сброса, из-за чего `low_level_input()` перестаёт вызывать `HAL_ETH_ReadData()` вообще (гейт `if (RxAllocStatus == RX_ALLOC_OK)`) — тогда модуль продолжает отправлять SYN (PC видит и ARPит его), но никогда не обрабатывает входящий SYN-ACK.

**Применены два фикса для проверки (собраны, НЕ ПРОВЕРЕНЫ на плате):**
1. `ethernetif_reset()` теперь дополнительно вызывает `etharp_cleanup_netif(netif)` — очищает ARP-таблицу lwIP (программное состояние, не аппаратное; наш сброс трогал только периферию ETH, а ARP-кэш lwIP мог оставаться "грязным" между циклами — это согласуется с давним наблюдением пользователя "помогает только сброс по питанию", т.к. питание пересоздаёт весь lwIP с нуля через `lwip_init()`, а наш софт-ресет — нет).
2. `RxAllocStatus` → переименован в публичный `g_eth_rx_alloc_status` (`ethernetif.h`), добавлен в heartbeat: `[alive] ... rxalloc=N` (main.c). `0` = `RX_ALLOC_OK`, `1` = `RX_ALLOC_ERROR`. Если в следующем тесте `rxalloc=1` будет видно во время зависания — это подтвердит гипотезу про исчерпание RX_POOL.

**Результат теста:** `rxalloc=0` все 100% времени, включая момент постоянного зависания — гипотеза про истощение RX_POOL **отклонена**. `etharp_cleanup_netif()` тоже не помог — цикл "сброс → мгновенный connection error" продолжился без изменений.

**Новая улика:** после сброса `[tcp_echo] connection error, will retry` появляется **мгновенно**, без обычной 5-секундной паузы нашего собственного таймера подключения. Это означает, что это НЕ наш `tcp_abort()`-по-таймауту (который быждал `RECONNECT_INTERVAL_MS`), а настоящий немедленный RST из сети. Рабочая гипотеза: коммутатор/роутер видит частые down/up на порту модуля (каждый `ethernetif_reset()` дёргает линк) и включает защиту от "флаппинга" порта — временно блокирует/игнорирует порт после нескольких быстрых переключений состояния линка за короткое время. То есть **наши собственные частые сбросы ETH могут быть причиной того, что сеть не восстанавливается**, а не лечением.

**Применённый фикс (собран, НЕ ПРОВЕРЕН):** экспоненциальный backoff между `ethernetif_reset()` (`tcp_echo_client.c`): `s_reset_count` считает подряд идущие сбросы без единого успешного подключения; задержка перед следующей попыткой подключения после сброса = `RECONNECT_INTERVAL_MS << min(s_reset_count, 4)`, то есть 5с → 10с → 20с → 40с → 60с (потолок `ETH_RESET_BACKOFF_CAP_MS`). Сбрасывается в 0 при любом успешном `[tcp_echo] connected`. В лог добавлено сообщение `[tcp_echo] backoff Nms before next try`.

**Найден баг в самом backoff-фиксе (тест показал):** в логе сообщение "backoff 40000ms before next try" печаталось, но реальная пауза перед следующим сбросом была всего ~10 секунд — backoff не действовал. Причина: в `tcp_echo_client_poll()`, `case ECHO_STATE_CONNECTING` (таймаут SYN без ответа), код вызывал `tcp_abort(s_pcb)` (это синхронно вызывает `on_err()`, который сам корректно вызывает `reset_to_idle()` и при необходимости выставляет backoff), а СРАЗУ ПОСЛЕ — ещё раз unconditionally вызывал `reset_to_idle()`, которая просто заново выставляла `s_next_action_tick = HAL_GetTick() + RECONNECT_INTERVAL_MS` (5с), затирая backoff. **Исправлено**: теперь при `s_pcb != NULL` `reset_to_idle()` вызывается только один раз (внутри `on_err()`, через цепочку `tcp_abort`), без повторного затирания снаружи. Собрано, **ЕЩЁ НЕ ПРОВЕРЕНО на плате**.

**Тест на другом порту роутера (2026-06-18): проблема повторилась идентично.** Это ИСКЛЮЧАЕТ теорию про flap-protection свича — проблема не во внешней сети, она в модуле. При этом `txbuf` снова вырос до ~50-53 несмотря на фикс дренажа дескрипторов (фикс не дал измеримого эффекта на пик — осталось почти так же, как без него, просто без фикса было 104, с фиксом ~50-53; ещё предстоит понять, почему дренаж не справляется полностью).

**Ключевое совпадение, объясняющее ВСЁ:** порог зависания (~50-53 пакетов) **не зависит от паузы между пакетами и не зависит от порта свитча** — то есть зависит только от КОЛИЧЕСТВА переданных пакетов, не от времени и не от внешней сети. При `MEM_SIZE=16KB` и примерной накладной стоимости ~300 байт на pbuf (текст ~70-90 байт + служебные данные lwIP), `16384/300 ≈ 54` — это совпадает с порогом практически точно. Это означает: лежащая в основе TX-утечка (pbuf, висящий с лишней ссылкой из-за `HAL_ETH_ReleaseTxPacket()`) всё ещё исчерпывает кучу lwIP `MEM_SIZE`, и именно ЭТА куча — программное состояние lwIP, а не аппаратная часть ETH — никогда не восстанавливалась нашим `ethernetif_reset()` (он трогает только MAC/DMA/PHY + ARP-таблицу, но не `mem_init()`/`memp_init()`). Это объясняет давнее наблюдение пользователя "помогает только сброс по питанию" — питание это единственное, что раньше пересоздавало кучу lwIP с нуля.

**Применённый фикс (собран, ЕЩЁ НЕ ПРОВЕРЕН):** `ethernetif_reset()` теперь дополнительно вызывает `dhcp_stop(netif)` + `mem_init()` + `memp_init()` — полный сброс кучи lwIP (`MEM_SIZE`) и всех стандартных memp-пулов (TCP_PCB, TCP_SEG, PBUF, UDP_PCB и т.д.), той самой памяти, которую раньше реально пересоздавал только физический сброс питания. Безопасно вызывать в этой точке, так как `TxDescList`/`RxDescList` уже обнулены ВЫШЕ в той же функции — никто больше не должен ссылаться на старую кучу. `RX_POOL` (кастомный пул через `LWIP_MEMPOOL_DECLARE`) отдельный от стандартных memp-пулов и не трогается этим вызовом — он уже переинициализируется внутри `low_level_init()`.

**Тест показал первый РЕАЛЬНЫЙ HardFault за всю сессию** (наша диагностика наконец сработала!): `[HARDFAULT] PC=0x08007464 LR=0x00000000 ...` сразу после `[eth] HAL_ETH_Init OK` при аварийном `ethernetif_reset()`. По `.map`-файлу (`arm-none-eabi-addr2line`/`nm --numeric-sort`) PC попал точно в `low_level_output()` (`ethernetif.c`).

**Причина — баг в МОЁМ собственном предыдущем фиксе:** `dhcp_stop(netif)` останавливает DHCP-клиент, но НЕ освобождает структуру `struct dhcp`, которую `dhcp_start()` выделил через `mem_malloc()` ещё при загрузке — `netif->dhcp` продолжает на неё указывать. Сразу после этого `mem_init()` сбрасывает free-list ВСЕЙ кучи — та же память может быть выдана повторно под что-то другое, пока `netif->dhcp` всё ещё "висит" на ней. Первая же новая аллокация (DHCP/ARP-пакет после ресета) переписала эту память, и тогда что-то внутри DHCP-обработки (или просто следующий `low_level_output()`, работающий с уже мусорным pbuf) обратилось к испорченным данным → HardFault.

**Исправлено:** перед `mem_init()` добавлен `dhcp_cleanup(netif)` (реально делает `mem_free()` структуры и очищает client-data слот netif — нашёл в `Middlewares/Third_Party/LwIP/src/core/ipv4/dhcp.c:712`). Также добавлен `dhcp_start(netif)` после `low_level_init()` — закрывает отдельный, ранее не замеченный гэп: ни `ethernetif_reset()`, ни `low_level_init()` сами по себе никогда не перезапускали DHCP-клиента после сброса (это делают только `MX_LWIP_Init()` при загрузке и `ethernetif_poll_link()` при переходе линка из down в up) — то есть после каждого нашего софт-ресета модуль работал на старом IP без активной DHCP-аренды вообще.

Собрано, **ЕЩЁ НЕ ПРОВЕРЕНО на плате**.

**ПОДТВЕРЖДЕНО ТЕСТОМ (2026-06-18): главная цель достигнута.** HardFault не повторился. Модуль теперь **дважды за один сеанс сам восстановился** после аварийного `ethernetif_reset()` (`[tcp_echo] connected` после `backoff 5000ms` — впервые за всю сессию отладки!). Цикл стал самовосстанавливающимся: работает ~85-100 сек (пока `txbuf` растёт до ~50-53 и куча lwIP не исчерпывается) → связь рвётся → аварийный сброс (теперь со сбросом `mem_init()`/`memp_init()`/DHCP) → успешное переподключение. Раньше после первого разрыва модуль навсегда зависал без физического ресета — это и было главной проблемой пользователя, и она решена.

**Что осталось не идеальным (не блокирует работу, но стоит доделать при следующем заходе):** утечка TX-дескрипторов (`HAL_ETH_ReleaseTxPacket()`, см. выше) всё ещё не устранена до конца — `txbuf` всё равно доходит до ~50-53 при активном обмене вместо удержания около 0, из-за чего связь периодически обрывается и требует аварийного сброса. Теперь это не катастрофа (само восстанавливается), но было бы лучше не доходить до этого вовсе. Следующий шаг при желании докопаться: добавить точечную диагностику внутри цикла дренажа в `low_level_output()` (`ethernetif.c`) — почему он не успевает полностью разгрузить кольцо дескрипторов во время быстрой серии пакетов.

### Параллельно найденный (не связанный) баг: индикатор LED2/GREEN не горит — ОКОНЧАТЕЛЬНО ДИАГНОСТИРОВАН (2026-06-18)

(Две промежуточные версии объяснения — "резистор электрически мешает PHY" и "pad2 сам выдаёт REFCLKO" — были опровергнуты пользователем экспериментально/по датащиту и отброшены.)

**Подтверждено по реальной схеме проекта (`f407.sch`) + datasheet SMSC "Schematic Checklist for LAN8720I" (`LAN8720AIQFNRevASchematicChecklist.pdf`, рис. 7, стр. 15):**

- `LAN8720I QFN` pin 2 = `LED2/!NINTSEL` — двухфункциональный: при POR/nRST это strap-вход `nINTSEL`, после защёлкивания — постоянный выход индикатора `LED2`.
- В схеме (`f407.sch`): GREEN LED физически встроен в разъём `J1` (RJ45 с LED), а не дискретный компонент. Цепь: `+3.3V → R12 (1кОм) → сеть "+GREEN" → J1 pin9 (анод)`; `J1 pin10 (катод) → сеть "-GREEN" → напрямую на pin2 PHY (LED2/!NINTSEL)`. Также на этой же сети висит `R37 pin1`, а `R37 pin2` сидит на `+3.3V` — это и есть исходная ошибка из памяти проекта ("R37 wired to +3V3 instead of GND"), из-за которой понадобился ручной аппаратный bodge-резистор 1кОм с pin2 на GND, чтобы получить `nINTSEL=0` (нужно для REFCLKO-режима, без которого `HAL_ETH_Init` не работает).
- По datasheet (рис. 7): `nINTSEL=1` → LED активен по **низкому** уровню, разводка `VDD2A → LED → R → pin2` (это ТОЧНО схема в `f407.sch`). `nINTSEL=0` → LED активен по **высокому** уровню, разводка должна быть `pin2 → LED → R → GND` (обратная).

**Корень проблемы:** аппаратная разводка GREEN LED сделана под `nINTSEL=1` (анод на VDD2A, катод прямо на pin2), а реально используемый strap — `nINTSEL=0` (обязателен для REFCLKO). При активном-высоком режиме PHY поднимает pin2 почти до уровня VDD2A для индикации — на LED исчезает разность потенциалов, и он не зажигается (в худшем случае логика индикации просто инвертирована, а не корректна). **Это чисто пассивное рассогласование полярности, не лечится прошивкой/регистрами PHY.**

**Возможное исправление (требует аппаратной правки, не сделано):** поменять, что приходит на `J1 pin9`/`pin10` — `pin9` (сейчас через R12 на +3.3V) перевести на прямое соединение с pin2 PHY; `pin10` (сейчас прямо на pin2) перевести через резистор (R12 или R37) на GND. Это требует перепайки 1-2 проводников/резисторов на платe. Без этого GREEN не может корректно индицировать, пока REFCLKO-режим обязателен.

**Статус: диагноз закрыт окончательно, аппаратное исправление отложено (не блокирует сетевую функциональность — LED2 не участвует в линиях данных RMII).**

**Обновление аппаратуры (2026-06-19):** пользователь удалил `R37` (был ошибочно подключён к +3.3V) и заменил временный bodge-резистор 1кОм на постоянный **6.8кОм** между pin2 и GND — тот же штатный pull-down для `nINTSEL=0`, просто на чистом одиночном резисторе вместо связки "неправильный R37 + самодельный бодж". Полярность GREEN LED (J1 pin9/pin10) **не менялась** — описанное выше рассогласование активного-высокого/активного-низкого режима остаётся в силе, индикатор по-прежнему не будет корректно зажигаться без отдельной перепайки J1. Эта правка касается только надёжности strap-цепи, не связана с багом генератора REFCLKO ниже (разные пины: nINTSEL = pin2, кварц = pin4/5).

**Финально подтверждено поведение (2026-06-19): LED2/GREEN — это индикатор Link (не Activity), инвертированный.** Наблюдение пользователя: с подключённым кабелем GREEN вспыхивает на ~1 сек (при появлении линка/автопереговорах) и гаснет; без кабеля горит постоянно. Это ровно то, что предсказывает теория инверсии: при `nINTSEL=0` PHY держит pin2 HIGH когда линк есть и LOW когда линка нет, а LED (разводка под активный-низкий) зажигается именно от LOW — то есть светится, когда линка НЕТ, и гаснет, когда линк есть (вспышка на ~1 сек — переходный период автопереговоров сразу после сброса PHY, пока pin2 ещё не перешёл в HIGH). Индикатор полностью исправен функционально, просто показывает обратную логику. Вопрос про LED2 закрыт окончательно — никаких новых неясностей не осталось, остаётся только опциональная аппаратная перепайка J1 pin9/pin10, если нужна нормальная (не инвертированная) индикация.

### ОКОНЧАТЕЛЬНЫЙ ФИКС TX-утечки дескрипторов (2026-06-18)

Пользователь настоял на полном устранении утечки (не только самовосстановлении): "конечно устранить! этот дефект является одним из важнейших".

**Точная диагностика (новая verbose-инструментация дренажа в `low_level_output()`):** на КАЖДОМ вызове, всю сессию, лог показывал `idx=0 hadPkt=0 desc0=0x30D00000 before=N after=N` — то есть `releaseIndex` навсегда застыл на 0, слот 0 пуст (`PacketAddress[0]==NULL`), а `BuffersInUse` (`before`) тем не менее растёт от реальных передач через другие слоты кольца. Дренаж не делал ни одной успешной итерации НИКОГДА.

**Найден точный баг в самом HAL (`Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_eth.c:1451-1535`, `HAL_ETH_ReleaseTxPacket()`):** функция идёт по кольцу начиная с `releaseIndex`, до `BuffersInUse` итераций, ПРОПУСКАЯ пустые слоты (`PacketAddress[idx]==NULL`) только ЛОКАЛЬНО (`idx++` в переменной на стеке) — `dmatxdesclist->releaseIndex` и `dmatxdesclist->BuffersInUse` обновляются ТОЛЬКО внутри ветки успеха (когда находит слот с `PacketAddress!=NULL && OWN==0`, строки 1519-1525). Если по пути встречается хоть один слот с `OWN` ещё установленным — функция немедленно прерывается (`pktTxStatus=0`) и ВЕСЬ локальный прогресс (включая уже пройденные NULL-пропуски) отбрасывается, ничего не коммитится назад в handle. Дальше та же ситуация повторяется на каждом следующем вызове — `releaseIndex` навечно замирает.

Отдельно: `ETH_Prepare_Tx_Descriptors()` (строка 3137-3141) отказывается повторно использовать слот кольца, если `PacketAddress[idx] != NULL` — **даже если `OWN` уже снят** (пакет реально ушёл в сеть). Единственный штатный механизм очистки `PacketAddress[]` — сломанный `HAL_ETH_ReleaseTxPacket()` выше. Итог: слоты с уже переданными пакетами навсегда остаются "занятыми" программно → `BuffersInUse` только растёт → каждый такой pbuf держит лишнюю ссылку (`pbuf_ref()` в `low_level_output()`) → куча lwIP (`MEM_SIZE`=16KB) исчерпывается через ~50-54 пакета (совпадает с прошлым расчётом `16384/300≈54`).

**Фикс (применён, см. `Core/Src/ethernetif.c`):** перестали доверять бухгалтерии HAL вообще. Старый verbose drain-loop в `low_level_output()` заменён на новую функцию `eth_tx_drain_all()`, которая каждый вызов обходит ВСЕ `ETH_TX_DESC_CNT` физических слотов кольца напрямую (не используя `releaseIndex`/`HAL_ETH_ReleaseTxPacket()`): если `PacketAddress[idx]!=NULL && OWN==0` — слот реально готов, вызывается `HAL_ETH_TxFreeCallback()` (= `pbuf_free()`) и `PacketAddress[idx]` обнуляется; иначе слот считается ещё занятым. После обхода `BuffersInUse` и `releaseIndex` пересчитываются с нуля из реального состояния кольца. Это устраняет саму возможность "застревания" — больше нет общего `releaseIndex`, который можно заклинить, и `PacketAddress[]` всегда отражает реальное состояние, так что `ETH_Prepare_Tx_Descriptors()` больше никогда не откажет на основании устаревшей записи.

Собрано, билд проходит (`cmake --build build`), **ещё не проверено на плате** — следующий шаг: прошить и прогнать длительный тест (как раньше, burst трафика на протяжении нескольких минут), убедиться что heartbeat-поле `txbuf=` теперь держится около 0-1 постоянно (а не растёт до 50+), и что `ethernetif_reset()`/backoff-цикл больше не требуется вовсе.

**ПОДТВЕРЖДЕНО ТЕСТОМ (2026-06-18): TX-утечка дескрипторов устранена.** `txbuf=1` держался стабильно весь 270-секундный прогон (раньше к 50-53 пакету уходил в рост и связь рвалась). `eth_tx_drain_all()` работает как задумано — фикс TX-утечки закрыт, можно больше не возвращаться к этой части.

### Новый, отдельный баг: TCP-клиент замолкает навсегда после одного `connection error`

После исправления TX-утечки нашёлся СЛЕДУЮЩИЙ дефект, ранее маскировавшийся постоянными зависаниями ETH. Симптом: один раз проходит `[tcp_echo] connection error, will retry`, после чего — полная тишина в TCP-логике на 220+ секунд (никаких "connected"/"connection error"), хотя `[alive]` heartbeat продолжает идти каждые 5 сек и `arp -a` подтверждает, что модуль виден в сети. **Значит зависла не прошивка и не ETH/IP-стек, а конкретно state-машина в `tcp_echo_client.c`.**

Найдены два места в `start_connect()` (`tcp_echo_client.c`), которые при ошибке молча уходили в `reset_to_idle()` без единого сообщения в лог: `tcp_new() == NULL` (исчерпан `MEMP_NUM_TCP_PCB`, в `lwipopts.h` всего `4`) и `tcp_connect() != ERR_OK`. Если стейт-машина попадает в один из этих путей, она будет повторять попытку каждые 5 сек молча, бесконечно — внешне выглядит как полное зависание, хотя на самом деле просто крутится вхолостую без единого вывода.

**Фикс (применён):** добавлены `rx_push()` с текстом ошибки в оба этих места (`tcp_new() failed (PCB pool exhausted?)` и `tcp_connect() failed err=N`). Также добавлена однобуквенная диагностика состояния `tcp_echo_client_state_char()` (`'I'`=idle, `'C'`=connecting, `'E'`=connected/established), выведенная в heartbeat как новое поле `tcp=` (`main.c`): `[alive] t=... eth=... txbuf=... rxalloc=... tcp=I/C/E`.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, повторить тест до момента "зависания", прочитать `tcp=` в heartbeat (покажет, застряла машина в `C` (CONNECTING — SYN ушёл, ответа нет) или крутится в `I` (IDLE — `start_connect()` падает на одном из двух теперь залогированных путей)), и/или дождаться появления нового сообщения `tcp_new() failed` / `tcp_connect() failed err=N` в логе.

**ПОДТВЕРЖДЕНО ТЕСТОМ (2026-06-18): `tcp_connect() failed err=-1` = `ERR_MEM`.** Лог дал точные числа: `heap=16312/16384 tcp_pcb=1/4 tcp_seg=0/16 pbuf=0/8` (формат `used/avail`). Пулы `TCP_PCB`/`TCP_SEG`/`PBUF_POOL` практически пустые — значит утечка не в счётчиках сегментов/PCB, а в самой куче lwIP (`MEM_SIZE`=16KB, `mem_malloc()`), которая была занята на 16312 из 16384 байт (свободно всего 72 байта).

### Второй, отдельный баг: утечка кучи lwIP в `tcp_write()` (не связан с TX-дескрипторами)

Добавил поле `heap=used/avail` в heartbeat (`main.c`, через `lwip_stats.mem`) — это показало рост в реальном времени, не только в момент сбоя. **Результат теста:** куча росла **с каждым отправленным сообщением** во время активного обмена (`1476→1856→5472→16056→16264→16344` за ~30 сек активной переписки), затем **переставала расти** ровно когда переставали печатать, и **не падала** даже после 20+ секунд полного простоя без нового трафика — то есть это настоящая утечка (не задержка ACK), и она привязана к каждой передаче через `tcp_write()`, а не к разрыву соединения.

**Причина:** `TCP_OVERSIZE` в lwIP по умолчанию равен `TCP_MSS` (1460 байт) — каждый `tcp_write()`, который начинает новый "хвостовой" непосланный сегмент, резервирует в куче этот запас, чтобы последующие мелкие записи могли дописываться в тот же сегмент без новой аллокации. В `tx_flush()` (`tcp_echo_client.c`) после каждого `tcp_write()` сразу вызывается `tcp_output()` — то есть каждое сообщение становится отдельным "хвостом" с собственным резервом ~1460 байт, который не переиспользуется следующей записью (это уже новый сегмент). Магнитуда роста (~1400-1500 байт на сообщение) точно совпала с `TCP_MSS`, подтвердив диагноз.

**Фикс (применён, `Core/Inc/lwipopts.h`):** `#define TCP_OVERSIZE 0` — официально поддерживаемое значение (см. комментарий в `lwip/opt.h`: "0: Don't oversize, always allocate the exact size"), отключает резервирование запаса полностью; `tcp_pbuf_prealloc()` будет выделять ровно нужный размер на каждую запись. Для нашего паттерна использования (всегда `tcp_output()` сразу после `tcp_write()`) это не теряет производительность, так как мы и не пользовались переиспользованием запаса.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, повторить тот же тест (несколько сообщений через UART подряд), убедиться что `heap=` в heartbeat теперь держится стабильно низко (не растёт пропорционально количеству сообщений), и что `tcp_connect()` больше не падает с `ERR_MEM` после/во время длительного обмена.

**ТЕСТ (2026-06-18): `TCP_OVERSIZE=0` уменьшил рост кучи (~1400→~150-250 байт/сообщение), но НЕ устранил его.** Куча всё равно дошла до предела (`16384/16384`) за ~75 сек активного обмена и `tcp_connect()` снова упал с `ERR_MEM`. Значит `TCP_OVERSIZE` был не единственной причиной — есть утечка и в самих данных (не только в запасе под них). Также замечена аномалия: после одного `ethernetif_reset()` heap показал `17596/16384` — **больше объявленного объёма** (возможна порча счётчиков статистики или реальное повреждение памяти при сбросе, требует отдельной проверки).

**Новая диагностика (применена):** `tcp_echo_client_sndqueuelen()` (`tcp_echo_client.c`/`.h`) возвращает `tcp_sndqueuelen(s_pcb)` — число pbuf в очереди отправки PCB (`unsent`+`unacked`). Добавлено в heartbeat как `sndq=` (`main.c`). Если это число растёт без остановки во время активного обмена (а соединение при этом продолжает работать) — значит ACK не освобождает отправленные данные, и утечка именно здесь, а не в "запасе" `TCP_OVERSIZE` и не в RX-пути.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, повторить тест, прислать лог с новым полем `sndq=` в heartbeat.

**Найден отдельный баг диагностики (2026-06-18): счётчик `lwip_stats.mem.used` не сбрасывается при `ethernetif_reset()`.** В длинном тесте (t=480-505 сек, уже после нескольких циклов аварийного сброса) heap показал `38492/16384` — **больше объявленного объёма кучи**, при этом соединение продолжало работать (`tcp=E`, без `ERR_MEM`). Проверка `mem_init()` (`Middlewares/Third_Party/LwIP/src/core/mem.c:516`) показала: эта функция сбрасывает РЕАЛЬНЫЙ список свободных блоков аллокатора (поэтому настоящая куча действительно очищается, и работа после сброса продолжается нормально), но НЕ трогает `lwip_stats.mem.used` — это отдельная переменная статистики, обновляемая только инкрементами/декрементами при каждом malloc/free. После каждого `ethernetif_reset()` она просто продолжает копиться от старого значения, так что через несколько циклов сброса показывает фантастические числа, не отражающие реальное состояние кучи.

**Фикс (применён, `ethernetif_reset()` в `ethernetif.c`):** после `mem_init()`/`memp_init()` добавлен `memset(&lwip_stats.mem, 0, sizeof(lwip_stats.mem))` + `MEM_STATS_AVAIL(avail, MEM_SIZE)` — обнуляет счётчик статистики синхронно с реальным сбросом кучи. Это никак не влияет на сам факт утечки (она в реальном аллокаторе, не в счётчике) — это чисто чинит достоверность диагностики `heap=` в heartbeat после сброса.

**Важно: подлинность утечки в ПЕРВОМ цикле (до первого сброса) остаётся подтверждённой** — там `heap=16384/16384` совпало с настоящим падением `tcp_connect()` с `ERR_MEM` (это не могло быть просто артефактом счётчика, так как `ERR_MEM` возвращается реальным `mem_malloc()`, не основанным на статистике). Утечка реальна, просто после починки счётчика её будет проще отслеживать дальше.

Собрано, билд проходит, **ещё не проверено на плате** — нужно повторить тест с самого начала (после прошивки) и прислать ПЕРВЫЕ ~100 сек лога (до первого `ethernetif_reset()`), с полем `sndq=`, чтобы увидеть, растёт ли очередь отправки PCB в момент настоящей утечки.

**Результат теста: `sndq=0` всё время** (даже в момент `ERR_MEM`) — утечка не в очереди PCB. **Куча росла даже без единого набранного сообщения** (t=5000→105000, до первого "Hello Module" в логе) — рост шёл от автоматических `ping #N`, которые `tcp_echo_client_poll()` сам шлёт каждые `SEND_INTERVAL_MS`=2000 в состоянии CONNECTED. TCP keepalive здесь не виноват: он сбрасывается каждой передачей, а пинг идёт чаще интервала keepalive, так что последний физически не успевает сработать.

**Точная диагностика (добавлена в `low_level_output()`):** вывод `p->ref` пакета ПЕРЕД нашим `pbuf_ref()` — показал `ref=1` стабильно на каждом пакете (ожидаемое поведение, лишней ссылки до нас нет). Затем добавлена диагностика прямо в `eth_tx_drain_all()`: печать при каждом реальном освобождении слота. **За весь тест (~90+ передач) — НИ ОДНОЙ строки освобождения.** Значит `eth_tx_drain_all()` никогда ничего не находит для очистки, хотя `txbuf` (`BuffersInUse`) стабильно показывал `1`.

### НАЙДЕН ИСТИННЫЙ КОРЕНЬ ОБЕИХ УТЕЧЕК (TX-дескрипторов и кучи lwIP)

Прямая проверка источника `stm32f4xx_hal_eth.c` показала: `heth->TxDescList.CurrentPacketAddress` (то самое поле, которое `ETH_Prepare_Tx_Descriptors()` копирует в `PacketAddress[descidx]`, строка 3259) **устанавливается только внутри `HAL_ETH_Transmit_IT()`** (режим прерываний, строка 1048: `heth->TxDescList.CurrentPacketAddress = (uint32_t *)pTxConfig->pData;`). В `HAL_ETH_Transmit()` — **polling-режиме, который мы используем** (строки 962-1028) — это поле НИГДЕ не устанавливается!

Это означает: всё время, что мы вызывали `HAL_ETH_Transmit()`, `PacketAddress[]` никогда не получал указатель на реальный переданный pbuf — там всегда оставался NULL/устаревшее значение. Отсюда следует ВСЁ:
- `HAL_ETH_ReleaseTxPacket()` (старая HAL-функция) всегда видела `PacketAddress[idx]==NULL` и просто "пропускала" каждую запись — отсюда и самый первый баг сессии (рост `BuffersInUse` до 50-104 и обрыв связи).
- Наша замена `eth_tx_drain_all()` страдала ТЕМ ЖЕ корнем — она тоже ищет `PacketAddress[idx]!=NULL`, и тоже никогда не находила, поэтому ни разу не вызвала `pbuf_free()` для лишней ссылки, взятой нашим `pbuf_ref(p)`.
- Каждый переданный пакет навсегда оставлял ОДНУ лишнюю ссылку (`pbuf_ref()` без последующего `pbuf_free()`), которую lwIP сам никогда не отпускал, потому что эту ссылку добавляли МЫ, а не lwIP — и это и есть утечка кучи `MEM_SIZE`, которую гонялись всю сессию.

**Фикс (применён, `low_level_output()` в `ethernetif.c`):** перед вызовом `HAL_ETH_Transmit()` добавлена строка `EthHandle.TxDescList.CurrentPacketAddress = (uint32_t *)p;` — то же самое, что делает `HAL_ETH_Transmit_IT()` для режима прерываний. Теперь `ETH_Prepare_Tx_Descriptors()` корректно сохраняет реальный указатель в `PacketAddress[]`, и `eth_tx_drain_all()` сможет находить и освобождать его как положено.

Вся verbose-диагностика (`[eth] tx ...`, `[eth] drain free ...`) убрана из `low_level_output()`/`eth_tx_drain_all()` после нахождения причины — она была временной. `heap=`/`tcp=` в heartbeat (`main.c`) оставлены как полезные постоянные диагностические поля.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, прогнать длинный тест с активным обменом (как раньше), убедиться что `heap=` в heartbeat теперь держится стабильно низко неограниченно долго, `tcp_connect()` больше не падает с `ERR_MEM`, и аварийный `ethernetif_reset()`/backoff не требуется вовсе.

### ПОДТВЕРЖДЕНО: TX/heap-утечка устранена окончательно — НО найден новый баг: потеря IP без восстановления (2026-06-18, после ~2 часов наработки)

После фикса `CurrentPacketAddress` модуль проработал часами без роста кучи: `heap=128/16384` стабильно от t=7575000ms до t=8090000ms (больше 2 часов, замер до и после) — TX/heap-утечка закрыта окончательно, к этой части возвращаться не нужно.

**Новый, отдельный баг:** в это же время `tcp=I` (idle) без единого сообщения об ошибке, и модуль полностью пропал из сети — `arp -a` (полный, без фильтра) не показывает НИ ОДНОГО неизвестного адреса в подсети 10.0.1.x, только роутер/инфраструктуру/мультикаст. Модуль не отвечает ни под каким IP.

**Причина (подтверждена чтением исходников lwIP, `Middlewares/Third_Party/LwIP/src/core/ipv4/dhcp.c`):** при истечении DHCP-аренды (`dhcp_coarse_tmr()` → `t0_timeout` → `dhcp_release_and_stop()`, строка 1371) lwIP сам обнуляет IP интерфейса: `netif_set_addr(netif, IP4_ADDR_ANY4, ...)`, затем вызывает `dhcp_start()` для получения новой аренды. Это штатное поведение lwIP. НО: пока IP равен `0.0.0.0`, `main.c:133` (`if (netif_is_up(&gnetif) && !ip4_addr_isany_val(...)) { tcp_echo_client_poll(); }`) полностью пропускает вызов `tcp_echo_client_poll()` — а это значит, что наш ЕДИНСТВЕННЫЙ механизм самовосстановления (`ethernetif_reset()` после 3 неудачных TCP-подключений, `tcp_echo_client.c`) даже не успевает сработать, потому что вся его логика живёт внутри `tcp_echo_client_poll()`! Если DHCP не может сам переполучить аренду (по любой причине — таймаут ответа от роутера, потерянный broadcast и т.д.) — **нет вообще никакого механизма восстановления**. Здоровая сеть отвечает на DHCP DISCOVER за доли секунды; зависание на час+ означает, что DHCP-клиент lwIP застрял сам, и ничего извне его не подталкивает.

**Фикс (применён, `main.c`, основной `while(1)` цикл):** добавлен независимый от TCP watchdog. Считается время, прошедшее с момента, когда IP пропал (`ip_missing_since`, статическая переменная). Если IP отсутствует дольше `DHCP_STUCK_TIMEOUT_MS` = 90000 (90 сек — намного больше, чем нужно здоровой сети для DHCP) — вызывается тот же `ethernetif_reset(&gnetif)`, что и при зависании TCP (полный сброс ETH MAC/DMA/PHY + куча lwIP + перезапуск DHCP), независимо от состояния `tcp_echo_client_poll()`. Лог: `[lwip] no IP for too long, forcing ETH reset`.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, либо дождаться следующего естественного истечения DHCP-аренды (часы), либо для быстрой проверки временно уменьшить `DHCP_STUCK_TIMEOUT_MS` до маленького значения (например 10000) и принудительно вызвать `dhcp_release_and_stop()`/имитировать потерю IP, убедиться что `[lwip] no IP for too long, forcing ETH reset` появляется в логе и модуль восстанавливает IP/связь сам, без участия пользователя.

### Новый баг (2026-06-19): обрыв кабеля на 30-60 сек требует питания/полного ресета для восстановления

Симптом от пользователя: если выдернуть Ethernet-кабель на 30-60 сек, канал не восстанавливается сам по себе.

**Лог теста (см. диалог) показал необычную картину:** во время реального обрыва кабеля поле heartbeat `eth=` **не разу не показало `LINK_DOWN`** — оставалось `LINK_UP` непрерывно, пока `heap=`/`sndq=` росли (нормальное поведение TCP при потере пакетов: данные копятся неподтверждёнными, потом `tcp_echo` сдаётся с `connection error`). `eth=LINK_DOWN` появилось только ПОСЛЕ того, как штатный механизм "3 неудачных TCP-подключения → `ethernetif_reset()`" (`tcp_echo_client.c`) форсировал полный пересоздание MAC/DMA/PHY — то есть правильное определение обрыва линка проявилось только после полного ресета, а не в момент реального физического обрыва.

**Код `ethernetif_poll_link()` (`ethernetif.c:618`) и `LAN8742_GetLinkState()` (`lan8742.c:259`) выглядят корректно** — двойное чтение регистра `BSR` (стандартный приём против "залипшего" латч-бита Link Status), вызывается без всяких условий каждую итерацию главного цикла (`main.c:129`), внутри рейт-лимит 500мс. Видимых причин, почему PHY должен бы продолжать отвечать "линк есть" при физически выдернутом кабеле, в самом коде не нашлось — баг либо на уровне PHY-чипа/сигналов, либо где-то, что пока не видно по логам.

**Диагностика добавлена (применено, собрано, ещё не проверено на плате):** новое поле `phy=N` в heartbeat (`main.c`) — сырое возвращаемое значение `LAN8742_GetLinkState()` (см. `lan8742.h`: `1`=LINK_DOWN, `2..5`=варианты up, `6`=autonego not done, отрицательные = ошибка чтения/записи MDIO). Хранится в новой глобальной `g_eth_last_phy_link_state` (`ethernetif.h`/`.c`), обновляется на каждый вызов `ethernetif_poll_link()` прямо после чтения, до любой логики up/down. Цель — на следующем повторении того же теста увидеть: если `phy=` показывает `1` (PHY реально видит обрыв) пока `eth=` всё ещё `LINK_UP` — баг в логике `ethernetif_poll_link()`/netif (программный, легко чинится); если `phy=` показывает `2..5` (PHY настойчиво врёт "линк есть") при реально выдернутом кабеле — проблема на уровне PHY/сигналов RMII (аппаратная, сложнее).

**ПОДТВЕРЖДЕНО (2026-06-19): баг не специфичен к разрыву линка — это общая ненадёжность запуска генератора LAN8720 (кварц 25МГц + внутренний PLL) при сбросе через `nRST`.**

Тест дал три ключевых лога:
1. Не баг детектирования линка — баг в самом `HAL_ETH_Init()`.

Висело так навсегда (`eth=INIT_FAIL`), пока пользователь не сделал настоящий power-cycle.
3. **После настоящего отключения/включения питания — `HAL_ETH_Init OK` сразу, без единого сбоя**, и стабильно работает дальше.

**Вывод:** сброс через `nRST` (что эквивалентно нашему `ethernetif_reset()` И сбросу через отладчик/SWD — оба оставляют VDD PHY постоянно поданным) не гарантирует перезапуск кварцевого генератора LAN8720 — иногда генератор просто не стартует после такого "тёплого" сброса. Только полное снятие/возврат питания надёжно перезапускает его. Это классический симптом недостаточного запаса по запуску кварцевого генератора (margin кварца/нагрузочных конденсаторов/ESR относительно встроенного усилителя LAN8720), не специфичный для конкретного триггера (разрыв кабеля просто оказался одним из путей, ведущих к вызову `HAL_ETH_Init()` повторно — тем самым каждый раз есть тот же шанс на неудачный старт генератора).

**Статус: причина понятна, фикс не выбран.** Варианты (обсуждается с пользователем):

Модуль застрял в `INIT_FAIL`; включение сервера обратно через 355 сек не помогло, потому что модуль уже не выполнял Ethernet вообще (нужен power-cycle). **Значит баг триггерится ЛЮБЫМ событием, ведущим к `ethernetif_reset()`** (обрыв кабеля, падение сервера, DHCP-watchdog по таймауту и т.д.) — не специфика конкретно физического разрыва линии. Частота проявления на практике выше, чем предполагалось изначально.

**Фикс применён (2026-06-19, собран, ещё не проверен на плате):** `low_level_init()` (`ethernetif.c`) теперь повторяет `HAL_ETH_Init()` до `ETH_INIT_RETRY_COUNT`=5 раз (с `HAL_ETH_DeInit()` между попытками) перед тем как сдаться и перейти в `eth=INIT_FAIL`. Не устраняет корень (кварц всё равно может быть на пределе запаса по запуску), но даёт до 5 независимых попыток вместо одной перед тем как застрять — учитывая что баг вероятностный, это должно резко снизить частоту попадания в неисправимый `INIT_FAIL`. Лог покажет `[eth] HAL_ETH_Init retry N/5`, если потребовалась хоть одна повторная попытка — стоит обратить внимание, если это видно часто, значит запас по запуску действительно мал и стоит вернуться к аппаратному пути (конденсаторы кварца / managed power для PHY).

**ОПРОВЕРГНУТО ТЕСТОМ (2026-06-19): retry-loop не помогает — это не вероятностный сбой, а устойчивое зависание.** Все 5 попыток в retry-loop упали одинаково, дважды подряд (10/10 неудач за один сеанс, второй заход — через 90 сек по DHCP-watchdog). Если бы запуск генератора был просто "иногда не получается", шанс провалить 5 попыток подряд дважды подряд был бы исчезающе мал. Значит после срабатывания это не случайность, а стабильное "зависшее" состояние, из которого `nRST` не выводит вообще — классическая болезнь Pierce-генераторов: вместо колебаний попадает в статичное DC-равновесие, и обычно только снятие питания сбрасывает смещение достаточно, чтобы он снова смог завестись. Чисто программных способов сбросить именно эту аналоговую защёлку через `nRST` нет.

**Проверка по схеме:** конденсаторы нагрузки кварца (`C9`, `C10`) — 27пФ, в рекомендованном датащитом диапазоне (15-33пФ), запас в порядке. **Контрольный замер пользователя осциллографом:** сигнал на самом кварце (выводы XTAL1/XTAL2 микросхемы LAN8720) колеблется стабильно. Это говорит, что сырой кварцевый генератор исправен — но НЕ доказывает, что внутренний блок PHY, формирующий именно REFCLKO (pin14) из этого сигнала, тоже работает: это отдельный внутренний узел (PLL/буфер), который может зависать независимо от исправного кварца. Гипотеза уточнена: зависает не сам кварц, а внутренний PLL/буфер REFCLKO у PHY — то же объяснение "нужен сброс питания", просто узел немного другой.

**Диагностика добавлена (2026-06-19, собрано, не проверено на плате):** новая функция `eth_check_refclk_pa1()` (`ethernetif.c`) — временно переключает PA1 в режим входа таймера `TIM2_CH2` (AF1, "External Clock Mode 1") и считает число фронтов за ~1мс, затем возвращает PA1 в штатный режим ETH (AF11). Здоровые 50МГц на REFCLK дадут счёт в районе десятков тысяч за 1мс; если сигнал до STM32 не доходит — счётчик останется около 0. Вызывается автоматически сразу после провала всех 5 попыток `HAL_ETH_Init()`, печатает `[eth] PA1 edge count in ~1ms: N`. Это даёт программный контроль присутствия REFCLK на самом входе STM32 (PA1) без осциллографа, причём именно в момент сбоя — что точнее, чем разовый замер на кварце вручную.

Если число большое (тысячи+) — значит сигнал ЕСТЬ на PA1, и тогда дело не в PHY вообще, а в чём-то на стороне STM32/HAL (нужно копать дальше в `HAL_ETH_Init()`/`DMABMR.SWR` логике).

**ОКОНЧАТЕЛЬНО ПОДТВЕРЖДЕНО (2026-06-19): `PA1 edge count = 0` во всех трёх независимых случаях `INIT_FAIL` подряд за один сеанс.** Сигнал REFCLK реально не доходит до STM32 в момент сбоя — не предположение, а прямое программное измерение. В сочетании с осциллографом на кварце (генератор колеблется исправно) картина закрыта полностью:

- REFCLK на PA1 STM32 — отсутствует в момент `INIT_FAIL`, подтверждено программным счётчиком (0/0/0 за 3 случая).

**Вывод: зависает внутренний блок LAN8720, формирующий REFCLKO (pin14) из сигнала кварца (PLL/буфер) — не сам кварц, не дорожка/пайка между pin14 и PA1** (физический обрыв был бы постоянным и не лечился бы снятием питания, а у нас лечится). **Единственный оставшийся путь к программному решению (без участия человека): аппаратная доработка** — добавить управляемый ключ питания (load switch или P-MOSFET) в цепь VDD1A/VDD2A/VDDIO микросхемы U2 (LAN8720), управляемый свободным GPIO STM32, чтобы прошивка могла сама обесточить и заново включить PHY при обнаружении `PA1 edge count == 0`, вместо текущего тупика "нужен ручной power-cycle всей платы". Без этой доработки баг останется неустранимым программно — текущий retry-loop можно оставить (он не вредит, не мешает нормальной работе), но он не решает проблему.

**Статус: причина полностью и окончательно подтверждена. Решение требует аппаратной доработки (load switch на питание PHY) — ожидает решения пользователя, делать ли эту доработку.**

**ФИНАЛЬНОЕ ПОДТВЕРЖДЕНИЕ (2026-06-19), после всех программных фиксов этой сессии (ранний захват `nRST` в `main()`, 5-секундный импульс, `g_eth_hw_failed`, быстрая эскалация на `NVIC_SystemReset()`):** пользователь протестировал сценарий "сервер на ПК отвалился, через некоторое время снова включился" — связь НЕ восстановилась даже после рестарта МК (`NVIC_SystemReset()` через эскалацию) И даже после полной перезаливки новой прошивки (что эквивалентно рестарту по `nRST`/SWD, тоже не снимает VDD с платы). Восстановило только реальное физическое отключение/включение питания платы.

**Это окончательно закрывает вопрос о программном решении силами одного только `nRST`/перезапуска МК — он невозможен в принципе.** И `NVIC_SystemReset()`, и перезаливка через SWD, и ручной `nRST` — все они оставляют VDD PHY постоянно поданным, а зависает именно внутренний блок REFCLKO/PLL LAN8720, который сбрасывается только полным снятием питания (см. выводы выше). Единственный путь к полностью автоматическому восстановлению без участия человека — аппаратная доработка с управляемым ключом питания (load switch/P-MOSFET) на VDD1A/VDD2A/VDDIO микросхемы U2, управляемым свободным GPIO STM32, чтобы прошивка могла сама обесточить и заново включить именно PHY (не весь МК) при обнаружении `PA1 edge count == 0`. Без этой доработки — баг гарантированно требует ручного power-cycle при каждом попадании в это состояние, программно не лечится никак.

**Внешнее подтверждение (2026-06-19, по запросу пользователя — проверено в документации и на радиолюбительских форумах, это типовой чип LAN8720, не уникальная проблема нашей платы):**

Это объясняет МЕХАНИЗМ, а не просто эмпирический факт: `nRST` не может вылечить зависший REFCLKO/PLL не из-за недостаточной длины импульса, а потому что эта часть схемы в принципе не подключена к цепи сброса.

**НОВАЯ ПРОГРАММНАЯ ПОПЫТКА (2026-06-19), по настойчивому запросу пользователя ("не верю что нет софтового варианта разбудить lan8720") — найдена в самом датащите.** Перечитан официальный SMSC datasheet (LAN8720/LAN8720i Rev 1.0) целиком. Два релевантных факта:

Это прямое графическое подтверждение того, что `nRST` физически не обязан затрагивать генератор — ровно то, что показали и форумы (ESP32-форум: REFCLKO не останавливается во время `nRST`).
2. **Раздел 5.3.5.1 "General Power-Down"** — РЕГИСТР 0, БИТ 11 (`Power Down`), а не бит 15 (`Reset`, уже пробован и не помог — см. выше). Датащит: *"the entire transceiver, except the management interface, is powered-down... When bit 0.11 is cleared, the transceiver powers up and is automatically reset."* Это другой, ранее не пробованный механизм — пишется через MDIO, не трогает `nRST` вообще, описан как реально снимающий питание с "всего трансивера" (не просто сброс регистров, как делает бит 15), и при возврате из этого режима явно происходит автоматический ресет (то есть страпы типа `nINTSEL` должны перезащёлкнуться так же, как при `nRST`).

**Реализовано (`Core/Src/ethernetif.c`):** новая функция `eth_try_phy_power_cycle()` — сырой MDIO (те же регистры `MACMIIAR`/`MACMIIDR`, что и в диагностике `HAL_ETH_MspInit()`), сканирует адрес PHY, пишет `BCR=0x0800` (General Power-Down), ждёт 100мс, пишет `BCR=0x0000` (снятие power-down), ждёт ещё 100мс на запуск генератора, затем повторно меряет `eth_check_refclk_pa1()`. Вызывается в `low_level_init()` сразу после того, как retry-loop исчерпан и `PA1 edge count == 0` — **перед** эскалацией на `NVIC_SystemReset()`. Если REFCLK восстановился — `HAL_ETH_Init()` пробуется ещё раз немедленно, без перезагрузки МК. Если не восстановился — старая логика (счётчик отказов, при достижении порога `NVIC_SystemReset()`) работает как раньше, без изменений.

Собрано, билд проходит (14.19% FLASH / 40.77% RAM), **ещё не проверено на плате**. Следующий шаг: прошить, спровоцировать `INIT_FAIL`, смотреть лог — появится ли `[eth] phy power-cycle: trying General Power-Down...` и, если повезёт, `REFCLK recovered, retrying HAL_ETH_Init` без единой перезагрузки МК. Если этот путь сработает — это будет первое по-настоящему программное (без аппаратной доработки) решение всей проблемы.

**ПЕРВЫЙ ТЕСТ НА ЖЕЛЕЗЕ (2026-06-19): не помогло с задержкой 100мс.** Лог показал: `[eth] phy power-cycle: trying General Power-Down (BCR.11) toggle` — PHY отвечал по MDIO до и после (BCR=3000 в последующих диагностических дампах), но `low_level_init()` сразу вернул отказ (`eth=INIT_FAIL`, `g_eth_hw_failed=1`) — значит `eth_check_refclk_pa1()` после тоггла всё ещё показал 0. Старой диагностической строки с числом фронтов после тоггла не было (логировался результат только при успехе) — добавлено логирование `[eth] phy power-cycle: PA1 edge count after toggle: N` при любом исходе.

**Применено по аналогии с находкой про nRST:** возможно 100мс удержания `Power Down` недостаточно по той же причине, что и было с `nRST` (10мс не помогало, 5000мс — помогало) — остаточное смещение/заряд в генераторе может требовать секунд, а не миллисекунд, на спад. Увеличена выдержка `BCR=0x0800` (Power Down) с 100мс до **5000мс** перед снятием (`BCR=0x0000`), по образцу проверенного на железе фикса для `nRST`.

Собрано, билд проходит, **ещё не проверено на плате с новой 5-секундной выдержкой**. Следующий шаг: прошить, спровоцировать `INIT_FAIL`, смотреть `[eth] phy power-cycle: PA1 edge count after toggle: N` — если `N=0` снова, значит General Power-Down тоже не достаёт до зависшего блока (как и nRST), и программных вариантов по датащиту больше не остаётся — переходим к аппаратной доработке (load switch на VDD PHY).

**ОКОНЧАТЕЛЬНО ОПРОВЕРГНУТО (2026-06-19): `General Power-Down` с 5-секундной выдержкой ТОЖЕ не помог.** Лог на реальной плате (модуль был залит уже в зависшем состоянии — REFCLK мёртв с самого первого холодного старта): `PA1 edge count after toggle: 0` — то же самое, что и с короткой 100мс выдержкой. Оба документированных в датащите программных механизма (`nRST` и `BCR.11 General Power-Down`), с обоими вариантами длительности (короткой и 5-секундной), дают идентичный результат: генератор не восстанавливается. **Это исчерпывает все программные пути, найденные в датащите производителя.**

**Побочное подтверждение — быстрая эскалация работает как задумано:** в логе видно `t=22323ms` до первого `eth=INIT_FAIL` в heartbeat, затем быстрый (не 90-секундный) переход на `ethernetif_reset()` через `ETH_INIT_FAIL_RETRY_MS`, затем после второго подряд отказа — `NVIC_SystemReset()`. Полный цикл от холодного старта до перезагрузки МК ≈ 20-25 сек, что соответствует ожиданиям (фикс `g_eth_hw_failed` из этой сессии подтверждён работающим на железе).

**Итоговое поведение при зависшем генераторе: плата теперь просто бесконечно перезагружается по кругу** (~20-25 сек на цикл) без какого-либо прогресса, пока не будет снято питание руками — это лучше, чем зависание на минуты без всякой реакции (как было раньше), но программно проблему это не решает: REFCLKO/PLL-блок LAN8720 после зависания не восстанавливается ничем, что доступно через `nRST` или MDIO. **Подтверждено двойным независимым тестом (короткая и длинная выдержка для обоих механизмов) — дальнейших программных попыток по официальной документации не остаётся.**

**Статус: вопрос программного решения закрыт окончательно.** Единственный оставшийся путь к полностью автоматическому восстановлению без участия человека — аппаратная доработка с управляемым ключом питания (load switch/P-MOSFET) на VDD1A/VDD2A/VDDIO микросхемы U2, описанная выше. Текущий бесконечный reboot-loop можно оставить как есть (он не вредит, просто ждёт человека), либо добавить программный "тормоз" (например, прекращать попытки после N перезагрузок и просто гореть LED-индикатором ошибки, экономя циклы перепрошивки/износ) — но это не решает корень, только меняет поведение ожидания.

## НАСТОЯЩАЯ ПРИЧИНА НАЙДЕНА (2026-06-19): слабый резистор на страпе nINTSEL, а не зависание PLL

Пользователь справедливо усомнился в выводе "нужен ресет по питанию" для массового, повсеместно используемого чипа — и оказался прав. Пересмотр с нуля, по шагам:

1. **Проверка через датащит производителя и апноуты Microchip**: ни в одном референсном дизайне LAN8720 (включая собственный Application Diagram из датащита) нет управляемого ключа питания PHY — VDD1A/VDD2A/VDDIO всегда просто на шине 3.3В без доп. защиты. Если бы "зависание, лечится только питанием" было известным свойством чипа — производитель рекомендовал бы защиту. Это не нашлось ни у Microchip, ни в их апноутах.

2. **Осциллограф НЕЗАВИСИМО подтвердил программное измерение**, но дал ключевую деталь, которую программное измерение не видело: на ноге 14 (REFCLKO) во время сбоя — не "тишина на нуле", а **статичные +3.3В**. Это не сигнатура "зависшего посреди колебания генератора", а сигнатура **пассивно подтянутого неактивного входа/выхода** (как раз то, что даёт `nINT` в режиме ожидания — открытый сток с подтяжкой к VDD).

3. **Замер на ноге 2 (LED2/nINTSEL)** во время того же сбоя — тоже +3.3В. Сам по себе этот замер не различал две версии (нормальная работа LED2 в режиме REFCLKO тоже может давать HIGH), но навёл на гипотезу: если страп `nINTSEL` защёлкнулся в `1` (режим `nINT`/REF_CLK In) вместо нужного `0` (режим `REFCLKO`) — на ноге 14 будет неактивный `nINT` (статично HIGH через подтяжку), а REFCLKO просто не генерируется вообще, что идеально объясняет и статичный уровень, и работающий MDIO (SMI-блок не зависит от режима REF_CLK), и вероятностный характер бага (гонка при защёлкивании страпа на каждом сбросе, а не детерминированная аппаратная защёлка).

4. **Корень гонки**: страп `nINTSEL` (нога 2) до этого был притянут к GND резистором **6.8кОм** (см. историю проекта — раньше был кривой R37, потом подпайка 1кОм, потом заменено на постоянные 6.8кОм). Против внутренней подтяжки LAN8720 (**67кОм типично**, согласно датащиту, тип буфера IOPU) это даёт статически правильный низкий уровень (~0.3В), но **во время самого переключения `nRST`** (быстрый переходный процесс, наводки, паразитная емкость) тонкий резистор 6.8кОм мог не успевать гарантированно выиграть гонку за установившийся уровень к моменту защёлкивания (датащит, T11.2: "Configuration input setup to nRST rising" = min 200нс) — отсюда вероятностное, не 100%-ное попадание в правильный режим при каждом сбросе/перезапуске.

**Фикс (аппаратный, сделан пользователем 2026-06-19): резистор на ноге 2 заменён с 6.8кОм на 1кОм.** Это гораздо более уверенно выигрывает гонку против внутренних 67кОм (статический уровень ~0.04В вместо ~0.3В, и более быстрый RC-переход за счёт меньшего сопротивления при той же паразитной емкости). **После замены — проблема, по первому впечатлению пользователя, исчезла** ("похоже это решило проблему").

**Важная оговорка:** баг был вероятностным (не каждый сброс/перезапуск приводил к сбою), поэтому одного успешного теста недостаточно для полной уверенности — нужно понаблюдать за работой в течение длительного времени (несколько дней реальной работы, многократные перезапуски/циклы сервера/обрывы кабеля), прежде чем считать вопрос окончательно закрытым.

**Если фикс подтвердится длительным наблюдением:** это означает, что ВСЯ цепочка программных мер из этой и прошлых сессий (ранний захват `nRST` в `main()`, 5-секундная выдержка `nRST`, флаг `g_eth_hw_failed`, быстрая эскалация, `General Power-Down` через MDIO) боролась с СИМПТОМОМ (PHY иногда защёлкивается в нерабочий режим), а не с причиной. Это не значит, что эти меры бесполезны — быстрая эскалация и `NVIC_SystemReset()` всё равно дают automatic recovery даже в тех редких случаях, когда гонка всё же проигрывается (теперь реже, но физически возможность не исключена полностью, поскольку резистор всё равно конечен, а не идеальный короткий замыкатель) — но корневая причина была не "аппаратно неустранимое зависание PLL", а конкретный, дешёво исправимый страп-резистор.

**Уточнение (2026-06-19): зависание не вечное — самовосстановилось через несколько минут без участия питания.** Пользователь наблюдал самостоятельное восстановление связи спустя пару минут простого ожидания (90-секундный DHCP-watchdog продолжал вызывать `ethernetif_reset()` по таймауту; через несколько таких редких циклов одна из попыток сработала сама). Это меняет картину: зависание REFCLKO-блока — не постоянная защёлка, которую снимает только питание, а зависание с ОЧЕНЬ долгой постоянной времени восстановления через `nRST` (десятки секунд, не доли секунды). Быстрые повторы retry-loop (5 попыток за ~3 секунды, интервал ~600мс между ними) не дают этому времени — отсюда 10/10 неудач там. Редкие повторы (раз в 90 сек, через существующий watchdog) — дают, и через несколько таких попыток восстановление случилось без питания.

**Рабочая гипотеза:** скорее всего остаточный заряд/смещение в цепи генератора PHY не успевает стечь за доли секунды между быстрыми повторами retry-loop, но стекает за десятки секунд естественной утечки между редкими попытками watchdog'а.

**Открытый вопрос:** программный путь (редкие повторы, не частые) может оказаться рабочим решением без аппаратной доработки — НО неизвестно среднее время восстановления (минуты — приемлемо? десятки минут — нет?) и стабильность этого поведения (повторится ли так же надёжно в следующий раз). Нужно больше наблюдений, прежде чем считать вопрос закрытым программно.

**Применено (2026-06-19, собрано, не проверено на плате): растянутые интервалы в retry-loop.** `ETH_INIT_RETRY_DELAY_MS`=3000 (`ethernetif.c`) — добавлена пауза 3 сек перед каждым повтором `HAL_ETH_Init()` внутри `low_level_init()` (между `HAL_ETH_DeInit()` и следующим `HAL_ETH_Init()`), вместо прежних "впритык" повторов (~600мс между попытками). Цель — напрямую проверить и использовать гипотезу про долгую постоянную времени восстановления: 5 попыток с интервалом 3 сек дают ~15 сек суммарной растяжки внутри одного вызова `low_level_init()` (раньше — общая длительность одного вызова была ~3 сек). Блокирует главный цикл на это время, но это приемлемо — вызывается только когда ETH уже не работает (`ethernetif_reset()`/`INIT_FAIL`-восстановление), терять нечего.

Следующий шаг: прошить, дождаться `INIT_FAIL` в реальной работе, смотреть — стало ли восстановление чаще происходить уже ВНУТРИ самого retry-loop (видно по логу: меньше полных провалов "FAILED after retries", больше успешных `HAL_ETH_Init OK` после retry 2-5), а не только через внешний 90-секундный watchdog с интервалом в несколько циклов.

**НАСТОЯЩИЙ КОРЕНЬ И ФИКС НАЙДЕНЫ (2026-06-19): дело не в паузах между попытками, а в ДЛИНЕ самого импульса `nRST`.** Растягивание интервалов между retry не помогло. Пользователь проверил вручную: штатный импульс сброса (пинцетом замкнул pin15/nRST на GND) длиной **5 секунд** надёжно восстановил связь, в отличие от штатных **10мс**, которые держала прошивка (`HAL_ETH_MspInit()`, `stm32f4xx_hal_msp.c`). То есть внутреннему блоку REFCLKO/PLL PHY нужно гораздо дольше держать `nRST` в LOW, чтобы реально сбросить застрявшее состояние — 10мс (минимум по датащиту, обычно достаточный для штатного старта) недостаточно для восстановления именно из этого зависшего состояния.

**Фикс применён (`Core/Src/stm32f4xx_hal_msp.c`):** `HAL_GPIO_WritePin(...GPIO_PIN_RESET); HAL_Delay(10);` → `HAL_Delay(5000)` — держим `nRST` в LOW 5 секунд вместо 10мс, по аналогии с проверенным вручную фиксом. Это применяется при КАЖДОМ вызове `HAL_ETH_Init()` (значит и при обычной загрузке — будет на ~5 сек дольше один раз при старте, не критично).

**Сопутствующее (`Core/Src/ethernetif.c`):** т.к. настоящий фикс — длина импульса, а не пауза между попытками, убрана растянутая 3-секундная пауза между retry (была избыточна), `ETH_INIT_RETRY_DELAY_MS`→200, `ETH_INIT_RETRY_COUNT`→3 (retry-loop теперь просто дешёвая подстраховка, а не основной механизм восстановления).

Собрано, билд проходит, **ещё не проверено на плате**. Следующий шаг: прошить, дождаться/спровоцировать `INIT_FAIL` (выключить сервер на ПК или выдернуть кабель, дождаться 3 неудачных коннектов), проверить — восстанавливается ли уже с первой/второй попытки внутри retry-loop, без участия watchdog'а и без ручного питания.

**ОПРОВЕРГНУТО ТЕСТОМ (2026-06-19): 5-секундный `nRST` САМ ПО СЕБЕ не помог.** 9 неудач подряд (3 цикла сброса × 3 retry-попытки), каждый раз `PA1 edge count = 0`, идентично прежнему поведению. Длина импульса `nRST` оказалась не единственным фактором.

**Найдена вероятная причина:** в `HAL_ETH_MspInit()` (`stm32f4xx_hal_msp.c`) ПОСЛЕ аппаратного импульса `nRST` всегда дополнительно шёл программный MDIO-сброс PHY (`BCR=0x8000`, "restarts crystal osc + PLL", добавлен в одну из прошлых сессий как более ранняя попытка решить эту же проблему). Гипотеза: именно этот ДОПОЛНИТЕЛЬНЫЙ программный перезапуск PLL может сам не залочиться и заново сломать то, что только что успешно восстановил длинный `nRST` — а в твоём ручном тесте пинцетом такого второго шага не было вообще, только аппаратный `nRST`.

**Фикс применён (`stm32f4xx_hal_msp.c`):** убрана сама запись программного сброса (`MDIO_WR(...0x8000)`) и цикл ожидания/задержка 500мс после неё — оставлена только диагностика (чтение и вывод ID2/BCR/BSR/MCSR/SMR, это просто чтения регистров, безопасно). Теперь после смены strap'ов и пинов остаётся только 5-секундный аппаратный `nRST`, точно повторяя условия твоего успешного ручного теста.

Собрано, билд проходит, **ещё не проверено на плате**. Следующий шаг: прошить, спровоцировать `INIT_FAIL`, проверить — восстанавливается ли наконец с одной из попыток внутри retry-loop теперь, когда программный MDIO-сброс убран и остался только длинный `nRST`.

**ОПРОВЕРГНУТО ТЕСТОМ (2026-06-19): и это не помогло само по себе.** Даже без программного MDIO-сброса, retry-loop с длинным `nRST` не восстановил связь. Пользователь восстановил руками: во время перезапуска платы зажимал пинцетом линию `nRST` (вывод у `R3`) на землю.

**Найдена вторая причина:** между подачей питания и первым касанием `PB10` прошивкой (внутри `HAL_ETH_MspInit()`, вызывается из `MX_LWIP_Init()`) проходит `HAL_Init()` → `SystemClock_Config()` (старт HSE/PLL STM32) → `MX_GPIO_Init()` → инициализация UART1/UART3. Всё это время `nRST` PHY управляется только пассивным `R3` (10кОм pull-up) — PHY может выйти из сброса сам, пока питание/такты ещё не устоялись. Ручное удержание `nRST` с начала перезапуска (как делал пользователь) убирает это окно; программный сброс из `ethernetif_reset()` во время работы — не может, т.к. он просто переключает `nRST` заново уже посреди уже всё-равно стабильной работы платы, это другая ситуация.

**Фикс применён (`Core/Src/main.c`):** добавлен явный захват `PB10`/`nRST` в LOW самым первым действием в `main()`, сразу после `HAL_Init()`, до `SystemClock_Config()` и любой другой инициализации периферии. Реальные 5 секунд удержания + отпускание всё равно происходят позже, внутри `HAL_ETH_MspInit()` как раньше — но теперь `nRST` гарантированно прижат к земле с самого начала перезапуска прошивки, а не только начиная с того момента, когда код дошёл до `MX_LWIP_Init()`.

**Важная оговорка:** это помогает только полному перезапуску МК (кнопка ресета/питание/перепрошивка — что угодно, что заново выполняет `main()` с начала). Это НЕ помогает автоматическому восстановлению во время работы (`ethernetif_reset()` из watchdog'а внутри уже работающей программы, без перезапуска) — туда этот фикс не доходит, так как тот путь не проходит через начало `main()`.

**Эскалация добавлена (`Core/Src/main.c`, DHCP-watchdog):** если `ethernetif_reset()` через watchdog не помогает `ETH_RESET_ESCALATE_AFTER`=3 раза подряд (т.е. ~4.5 минуты без IP несмотря на попытки) — вместо очередной попытки `ethernetif_reset()` на месте прошивка теперь вызывает `NVIC_SystemReset()` — полный программный перезапуск МК. Это автоматически воспроизводит ручной приём пользователя (перезапуск + раннее удержание `nRST`) без участия человека. Лог перед этим: `[lwip] ETH reset escalation exhausted, rebooting MCU`.

Собрано, билд проходит, **ещё не проверено на плате**. Следующий шаг: прошить, спровоцировать продолжительный `INIT_FAIL` (например, временно уменьшить `DHCP_STUCK_TIMEOUT_MS` для быстрого теста), убедиться что после 3 неудачных `ethernetif_reset()` происходит `NVIC_SystemReset()` и связь восстанавливается уже после полной перезагрузки, без участия человека и без снятия питания.

**ТЕСТ ПОКАЗАЛ: даже ранний захват `nRST` в `main()` не спас от провала на самом первом холодном старте** — `HAL_ETH_Init FAILED`/`PA1 edge count: 0` сразу при включении, затем ещё 2 цикла `ethernetif_reset()` по 90 сек ожидания каждый — итого почти 4 минуты простоя, прежде чем должна была сработать эскалация (3 цикла × 90 сек). Пользователь справедливо спросил: зачем ждать целых 90 секунд между попытками, если `eth_check_refclk_pa1()` уже даёт однозначный ответ ("REFCLK=0") за секунды?

**Оптимизация скорости реакции (2026-06-19, `ethernetif.c`):** добавлен отдельный, более быстрый путь эскалации — счётчик `s_init_fail_streak` внутри `low_level_init()`, считает подряд идущие провалы именно `HAL_ETH_Init()` (а не общий "нет IP", как в `main.c`). При достижении `ETH_INIT_FAIL_REBOOT_THRESHOLD`=2 — `NVIC_SystemReset()` вызывается СРАЗУ, не дожидаясь 90-секундного DHCP-watchdog'а в `main.c`. Поскольку каждая попытка `low_level_init()` теперь и так занимает ~17 сек (3×retry с 5-секundным `nRST`), полный цикл до перезагрузки теперь ~34 секунды вместо ~4.5 минут. Старая эскалация в `main.c` (привязанная к общему "нет IP за 90×3 сек") оставлена как более медленный, общий fallback на случай других причин отсутствия IP (не связанных напрямую с провалом `HAL_ETH_Init()`, например застрявший DHCP при исправном ETH).

Собрано, билд проходит, **ещё не проверено на плате**.

**Найдена реальная причина, почему "ускорение" не было заметно (2026-06-19):** счётчик быстрой эскалации в `ethernetif.c` увеличивается только при ПОВТОРНОМ вызове `low_level_init()` — а единственное, что вызывает повторную попытку при полном отсутствии IP, это всё тот же медленный 90-секундный watchdog в `main.c` (быстрый 3-strikes механизм `tcp_echo_client.c` не запускается вообще, т.к. без IP `tcp_echo_client_poll()` не вызывается). То есть первые ~90 сек были неизбежны при прежней логике — быстрая эскалация просто не успевала получить второй шанс раньше.

**Фикс (`Core/Src/main.c`):** добавлен отдельный, короткий таймаут `ETH_INIT_FAIL_RETRY_MS`=2000 — если `g_eth_debug_marker == 100` (т.е. известно, что именно `HAL_ETH_Init()` провалился, а не "DHCP просто долго думает"), watchdog ждёт не 90 сек, а всего 2 сек перед повторной попыткой `ethernetif_reset()`. Теперь быстрая эскалация в `ethernetif.c` (порог 2 подряд провала) реально успевает сработать быстро: ~17 сек (первый провал при загрузке) + 2 сек + ~17 сек (второй провал) ≈ **36 секунд** до `NVIC_SystemReset()`, вместо прежних ~90+ секунд. Старый 90-секундный таймаут остался для другого, не пересекающегося случая — когда сама ETH-периферия в порядке, а просто DHCP-сервер долго не отвечает.

Собрано, билд проходит, **ещё не проверено на плате**. Следующий шаг: прошить, спровоцировать `INIT_FAIL` при загрузке, замерить реальное время до `NVIC_SystemReset()` — должно быть около 30-40 секунд, а не минуты.

**НАЙДЕН БАГ В САМОЙ ЛОГИКЕ БЫСТРОЙ ЭСКАЛАЦИИ (2026-06-19): условие `g_eth_debug_marker == 100U` в `main.c` НИКОГДА не было истинным.** При анализе очередного "свежего" лога обнаружилось: heartbeat показывал `eth=LINK_DOWN` вместо ожидаемого `eth=INIT_FAIL`, хотя `phy=-5` (замороженное значение `LAN8742_STATUS_READ_ERROR`) однозначно говорило, что `HAL_ETH_Init()` действительно провалился (это значение `ethernetif_poll_link()` даже не доходит до записи, т.к. в начале функции есть `if (EthHandle.gState != HAL_ETH_STATE_READY) return;` — а `gState` остаётся не-`READY` именно при провале `HAL_ETH_Init()`). Причина: `MX_LWIP_Init()` (`main.c`) вызывает `netif_add()`, которая внутри сразу вызывает `ethernetif_init()` → `low_level_init()` — и именно ТАМ при провале выставляется `g_eth_debug_marker = 100`. Но сразу после возврата из `netif_add()`, безусловно, идёт `g_eth_debug_marker = 52;` — затирая `100` буквально следующей строкой. Из-за этого: (а) heartbeat никогда не показывал `INIT_FAIL`; (б) условие `(g_eth_debug_marker == 100U) ? ETH_INIT_FAIL_RETRY_MS : DHCP_STUCK_TIMEOUT_MS` всегда выбирало медленный 90-секундный путь — то есть **весь предыдущий фикс с быстрым 2-секундным таймаутом фактически никогда не работал на практике**, хотя код был написан верно по отдельности.

**Фикс применён:** добавлен отдельный флаг `uint8_t g_eth_hw_failed` (`ethernetif.c`/`.h`) — пишется ТОЛЬКО в `low_level_init()`: `=1` при провале `HAL_ETH_Init()` после всех retry, `=0` при успехе. Больше ничто в проекте этот флаг не трогает, поэтому затереть его так же, как `g_eth_debug_marker`, не может. В `main.c` обе проверки (`ETH_INIT_FAIL_RETRY_MS` watchdog и heartbeat-форматирование `INIT_FAIL`/`LINK_UP`/`LINK_DOWN`) переведены на `g_eth_hw_failed`. `g_eth_debug_marker` оставлен как был — используется только для тонкой пошаговой диагностики внутри `low_level_init()`/`MX_LWIP_Init()`, для решения "сломан ли ETH" теперь не годится и не используется.

Собрано, билд проходит (**проверено локально через `cmake --build build`, без ошибок**), **ещё не проверено на плате**. Следующий шаг: прошить, спровоцировать `INIT_FAIL`, убедиться что heartbeat теперь действительно показывает `eth=INIT_FAIL`, и что полный цикл до `NVIC_SystemReset()` укладывается в ожидаемые ~30-40 сек, а не 90+.

**Добавлена печать даты/времени сборки прошивки при каждом перезапуске (2026-06-19, по явному запросу пользователя — "для исключения сомнений").** В `main()` (`Core/Src/main.c`), сразу после инициализации UART1 и перед `MX_LWIP_Init()`, добавлена строка лога `[boot] firmware built <DATE> <TIME>\r\n`, используя `__DATE__`/`__TIME__` — эти макросы подставляются компилятором на момент сборки конкретного `.elf`, поэтому не могут "устареть" в отличие от вручную поддерживаемого номера версии. Печатается при любом перезапуске — и холодном старте, и после `NVIC_SystemReset()` (escalation), что позволяет однозначно сопоставить присланный лог с конкретной прошитой сборкой.

## Подтверждение номинала страп-резистора по официальной схеме Microchip (2026-06-19)

Проверена официальная схема `EVB8720 Evaluation Board Schematic.pdf` (eval-плата LAN8720A от Microchip/SMSC, лист 2). Все страп-резисторы (REGOFF, MODE[0:2], PHYADD0) у вендора — **4.75 кОм 1%**. Для LED2/nINTSEL у них отдельная, ещё более жёсткая схема: `R2=0Ω` (прямая перемычка) + `R39=4.75кОм` в цепи самого светодиода — то есть вендор вообще не оставляет этот страп на слабой подтяжке. Это прямое подтверждение задним числом: бывший резистор **6.8кОм** на этой плате был слабее всего, что встречается в эталонной схеме производителя; поставленный **1кОм** — даже более решительный, чем рекомендация Microchip, и это нормально (запас, а не риск).

## Ускорение восстановления (2026-06-19): сокращены тайминги retry/reset, раз корень бага (страп) уже исправлен

Поскольку длинные выдержки (`nRST`=5с, MDIO power-down=5с) и большое количество повторов были защитными мерами под СТАРУЮ, неверную теорию ("неустранимое зависание PLL") — после нахождения настоящей причины (страп-резистор) они признаны избыточными и сокращены:

- `Core/Src/stm32f4xx_hal_msp.c`: hold `nRST` **5000мс → 2000мс**.
- `Core/Src/ethernetif.c`: `ETH_INIT_RETRY_COUNT` **3 → 1**; hold в `eth_try_phy_power_cycle()` **5000мс → 200мс** (этот MDIO-фолбэк подтверждённо тестами никогда не помогал ни на 100мс, ни на 5с — держать его долго бессмысленно).

Дополнительно, по логу с отдельным, новым отказом — ETH-железо и линк восстанавливаются нормально после `ethernetif_reset()` (`eth=LINK_UP`, корректный REFCLK), но DHCP не получает IP даже после пары программных сбросов подряд, при этом полный `NVIC_SystemReset()` решает за ~5 секунд. Раз мягкий сброс ненадёжен именно в этом отказе, сокращены тайминги до перехода к надёжно работающей перезагрузке:

- `Core/Src/main.c`: `DHCP_STUCK_TIMEOUT_MS` **90000 → 15000мс**; `ETH_RESET_ESCALATE_AFTER` **3 → 2**.

Итого худший случай зависания сократился с ~270+ секунд до ~30-40 секунд перед автоматической перезагрузкой МК. Собрано, билд проходит (`cmake --build build`).

**Открытый вопрос (не диагностирован до конца):** почему `ethernetif_reset()` не восстанавливает DHCP при том, что `dhcp_stop()/dhcp_cleanup()/mem_init()/memp_init()` выглядят корректными по исходникам lwIP (проверено: `dhcp_release_and_stop()` корректно декрементирует `dhcp_pcb_refcount` и зовёт `udp_remove()`, `udp_pcbs`/`tcp_active_pcbs` не должны оставаться "грязными" в этом сценарии, поскольку TCP-PCB ещё не создавался — `tcp=I` всё время). Похоже, причина не в учёте PCB в куче, а в чём-то другом (сетевая сторона — анти-флуд на сервере/роутере при повторных DISCOVER с того же MAC, либо момент вызова `dhcp_start()` относительно завершения автонеготиации PHY-линка). Текущая мера — не лечить, а быстрее переходить к перезагрузке, которая подтверждённо работает.

**ПОДТВЕРЖДЕНИЕ ПОЛЬЗОВАТЕЛЯ (2026-06-19): "пока работает - подхватывает отвалившийся сервер".** Первое реальное наблюдение того, ради чего всё затевалось изначально (модуль сам восстанавливает связь после падения и возвращения сервера, без участия человека) — похоже, заработало. Это первое позитивное подтверждение после сокращения таймингов; как и с резистором, нужно больше времени наблюдения, прежде чем закрывать тему окончательно.

## Веб-настройка таблицей + IP по умолчанию без DHCP (2026-09-24)

**Что сделано.** Страница `http://<IP модуля>/` (`Config/Src/config_http.c`) — таблица
«параметр | образец записи | текущее значение | новое значение» и кнопки
**Save** (записать во Flash, применить после рестарта — `device_config_store()` пишет
копию, не трогая рабочую в ОЗУ), **Cancel** (выйти без изменений), **Restart** (записать и
перезапустить). Подробности — `Config/README.md`.
В режиме DHCP, если сервер не ответил за 10 с, модуль берёт «IP по умолчанию» (поле
статического IP, из коробки `192.168.1.100/24`); на экране `DHCP: NO-DEFAULT IP`.

**Проблема 1: резервный IP ставился сразу при появлении линка.** Таймер стартовал как
`HAL_GetTick() | 1U` — при чётном тике старт на 1 мс в будущем, разность в ту же
миллисекунду = `0xFFFFFFFF` ≥ 10000. Исправлено отдельным флагом `dhcp_waiting`.

**Проблема 2 (главная): модуль уходил на 192.168.1.100 при живом роутере.** Лог UART:
модуль получал `10.0.1.140`, но TCP-сервер `10.0.1.16:5000` (ПК) не был запущен →
`tcp_echo_client` после 3 неудачных подключений вызывал `ethernetif_reset()` («сеть
зависла») → после этого сброса DHCP не проходит (давний открытый вопрос, см. выше) →
через 10 с резервный IP. Раньше это маскировал watchdog, перезагружавший МК через ~30 с.
Исправления:
- `tcp_echo_client.c`: `network_path_alive()` — если в ARP-таблице есть разрешённая
  запись сервера (или шлюза, если сервер вне подсети), значит TX и RX работают, отказ
  подключения = «сервер не слушает», ETH **не** сбрасывается. Сброс только для «глухой» сети.
- `main.c`: на резервном IP эхо-клиент не запускается (маршрута к серверу нет, его отказы
  только провоцировали сбросы).
- `main.c`: на резервном IP DHCP перезапускается каждые 30 с; если аренды нет 60 с и к
  веб-странице/порту 7000 никто не обращался (`device_config_touch()` /
  `device_config_last_access()`, 5 мин простоя) — `NVIC_SystemReset()`, как старая эскалация.
  Таймер не сбрасывается при кратком падении линка от `ethernetif_reset()` (из-за этого
  перезагрузка сработала только через 303 с вместо 70).

**Проверено:** тестовые сборки (резервный IP через 1 мс + принудительный `dhcp_stop()`)
— повтор DHCP возвращает `10.0.1.140`, без повтора срабатывает перезагрузка; рабочая
сборка — 90 с при незапущенном сервере: 8 отказов подключения, ни одного сброса ETH,
адрес держится. **Пользователь подтвердил после отключения питания: работает.**

**Как отлаживать:** лог — USART1 через CH340 (`COM6`, 921600); счётчики lwIP можно читать
на ходу без остановки МК: `openocd ... -c init -c "mdh <&lwip_stats> 12" -c shutdown`
(адрес из `arm-none-eabi-nm build/*.elf`). `openocd -c "reset run"` = программный сброс —
холодный старт он не воспроизводит, питание снимает только пользователь.
Внимание: `scripts/flash-progress.ps1` делает mass-erase — настройки из Flash сбрасываются
на значения по умолчанию.
