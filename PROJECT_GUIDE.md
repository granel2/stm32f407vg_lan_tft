# Проект STM32F407VG LAN v1

## Назначение
Файл сопровождения проекта описывает структуру, инструменты и шаги настройки, чтобы можно было открыть проект на другом компьютере без дополнительных вопросов.

## Содержимое проекта

- `stm32f407vg_lan_v1.ioc` — проект STM32CubeMX с конфигурацией МК и периферии.
- `.mxproject` — внутренний файл CubeMX для настройки генерации.
- `f407.sch` — схема платы в Autodesk Eagle.
- `EWARM/` — артефакты генерации IAR Embedded Workbench (EWARM), которые можно игнорировать, если вы не используете IAR.
- `Core/Inc/`, `Core/Src/` — пользовательский и сгенерированный код.
- `Drivers/` — STM32Cube HAL и CMSIS, необходимые для сборки.

## Окружение и инструменты

- STM32CubeMX 6.17.0 compatible
- STM32CubeF4 FW package V1.28.3
- ST-Link V2 или другой программатор, поддерживающий STM32F4
- Опционально: Autodesk Eagle для открытия `f407.sch`
- VS Code — основная среда редактирования

## VS Code

- В этом проекте `VS Code` используется как основной редактор исходников.
- Файлы CubeMX и исходники находятся в проекте, а `EWARM/` может оставаться в папке как сгенерированный артефакт.
- Сборка выполняется внешней цепочкой инструментов: `arm-none-eabi-gcc`, `make`, `CMake`, STM32CubeMX или другая система сборки.
- Программирование платы выполняется через `ST-Link V2` (клон) с помощью `STM32CubeProgrammer`, `OpenOCD`, `st-flash` или аналогичного инструмента.
- Если хотите, добавьте в `VS Code` задачи `tasks.json` для вызова сборки и прошивки.

## Целевая платформа

- Частота HSE: 25 MHz
- SYSCLK: 160 MHz
- Тактовая частота APB1: 40 MHz
- Тактовая частота APB2: 80 MHz

- `USART1` на PA9 (TX) / PA10 (RX), асинхронный режим, 921600 baud
- `USART3` на PD8 (TX) / PD9 (RX), асинхронный режим, 921600 baud
- `SWD` на PA13 / PA14
- `HSE` на PH0/PH1
- GPIO выходы для индикаторов:
  - PB4 = LED7
  - PB5 = LED8
  - PD0 = LED3
  - PD1 = LED4
  - PD4 = LED5
  - PD7 = LED6

## Важные примечания по открытию на другом компьютере

1. Скопируйте весь каталог проекта целиком, чтобы относительные пути сохранились. Проект использует относительные пути к `Core/`, `Drivers/` и `EWARM/`.
2. Откройте `stm32f407vg_lan_v1.ioc` в STM32CubeMX. Если пакет STM32CubeF4 V1.28.3 не установлен, установите его через менеджер пакетов CubeMX.
3. В генераторе CubeMX проверьте:
   - `Project Manager -> Project Name` = `stm32f407vg_lan_v1`
   - `Project Manager -> Keep User Code` = включено
   - `Project Manager -> Copy only the necessary libraries` = включено (или `Library copy = 1`)
4. Если вы используете собственную сборку, настройте параметры генерации так, чтобы получать только `Core/` и `Drivers/`, а не файлы IAR.
5. Если CubeMX пересобирает проект, любые изменения в `Core/Src/main.c` и `Core/Inc/main.h` должны сохраняться внутри специальных блоков `/* USER CODE BEGIN */` / `/* USER CODE END */`.

6. Программируйте плату через `ST-Link V2` (клон) с помощью `STM32CubeProgrammer`, `OpenOCD` или другого инструмента.

## КРИТИЧНО: startup_stm32f407xx.s должен содержать `.weak` для каждого обработчика

`Core/Startup/startup_stm32f407xx.s` — **не штатная генерация CubeMX** (CubeMX в этом проекте генерирует startup только для IAR, `EWARM/startup_stm32f407xx.s`). Файл для GCC/CMake был написан вручную при настройке CMake-сборки.

**Один раз уже была серьёзная ошибка:** в файле отсутствовали все директивы `.weak` перед строками вида `.thumb_set ИмяHandler, Default_Handler`. Без `.weak` эти имена (`SysTick_Handler` и вообще все ~80 обработчиков прерываний) становятся локальными алиасами на `Default_Handler` *внутри самого startup-файла*, и таблица векторов прерываний (`__isr_vector`) навсегда зашивает адрес `Default_Handler` — даже если в `Core/Src/stm32f4xx_it.c` есть нормальная реализация (например, `SysTick_Handler` с `HAL_IncTick()`). Компилятор и линковщик **не выдают ни одной ошибки/предупреждения** — всё линкуется "чисто".

Симптом был коварный: код без прерываний (GPIO, инициализация UART) работал нормально, прошивка успешно писалась и проверялась. Но как только код стал зависеть от прерывания (`HAL_Delay()` через `SysTick`), ядро намертво вешалось в `Default_Handler` (бесконечный `b .`) при первом срабатывании SysTick — `HAL_Delay()` никогда не возвращался. Внешне выглядело как "LED не мигают" / "зажглись и зависли".

**Если когда-нибудь снова придётся пересоздавать/чинить `startup_stm32f407xx.s` вручную:**
- Перед каждой строкой `.thumb_set XXX_Handler, Default_Handler` обязательно должна идти `.weak XXX_Handler`.
- Лучше вообще не писать этот файл руками — взять готовый `startup_stm32f4*.s` из пакета `STM32CubeF4` (`Drivers/CMSIS/Device/ST/STM32F4xx/Source/Templates/gcc/`) и подставить под нужный МК.
- Чтобы проверить, что баг не вернулся: halt ядро через OpenOCD дважды с разницей в пару секунд и командой `resume` между ними, прочитать `pc` и память по адресу глобальной переменной `uwTick` (см. `arm-none-eabi-nm build/*.elf | grep uwTick` для адреса) — если значения не меняются между чтениями, обработчики прерываний не работают.

## Прошивка через OpenOCD — известные проблемы и готовое решение

Эти грабли уже пройдены один раз (см. историю отладки) — **не наступайте на них снова**, просто используйте задачу `Flash STM32F407VG` из `.vscode/tasks.json`, она уже всё учитывает.

### Особенности этой платы (custom, `f407.sch`)

- **NRST от ST-Link к плате не подключён.** Аппаратный reset через `connect_assert_srst` недоступен.
- **BOOT0 (вывод 94 МК, U1) не выведен на джампер/разъём** — подтянут к GND резистором `R4` (10 кОм), и больше никуда. Чтобы временно поднять BOOT0 в "1" (например, для входа в системный bootloader), нужно физически припаивать временный провод на вывод 94 или на верхний контакт R4 — штатного способа нет.
- Напряжение на target обычно **~3.12–3.15 В** — на нижней границе нормы, но рабочее. Если когда-нибудь снова появится `init mode failed (unable to connect to the target)`:
  1. Это почти всегда обрыв/контакт SWDIO/SWCLK/GND, а не прошивка.
  2. Без NRST помогает приём "поймать момент после подачи питания": обесточить плату, в PowerShell крутить `openocd ... -c init -c halt` в цикле и включить питание во время цикла.

### Баг команды `program ... verify` в текущей сборке OpenOCD

Используемая сборка — `xPack OpenOCD 0.12.0+dev-02228-ge5888bda3-dirty`. На этой плате команда-шорткат
```
program build/stm32f407vg_lan_v1.bin verify reset exit
```
**стабильно проваливает верификацию** (`Error: checksum mismatch - attempting binary compare` → `Verify Failed`), даже когда запись реально проходит корректно. Перед ошибкой в логе всегда видно аномалию:
```
Info : flash size = 512 bytes
Warn : no flash bank found for address 0x00000000
```
— это внутренний баг авто-определения банка флеша именно в обёртке `program`, не реальная проблема платы/питания/прошивки (проверено: `RDP`/`WRP` отключены, `flash info 0` показывает все 12 секторов "not protected", напряжение в норме).

**Решение (уже встроено в задачу `Flash STM32F407VG`):** не использовать `program`, а делать запись и верификацию явными командами:
```
init
reset halt
stm32f4x mass_erase 0
flash write_image build/stm32f407vg_lan_v1.bin 0x08000000
verify_image build/stm32f407vg_lan_v1.bin 0x08000000
reset run
```
Это работает надёжно и подтверждено побайтовой верификацией — проверено и на пониженной (200/125 кГц), и на штатной (2000/1800 кГц) скорости SWD, оба раза успешно.

Скорость SWD **не ограничивается специально** — используется штатная из `target/stm32f4x.cfg` (~1.8 МГц). Разгон до 8 МГц, который встроен в хук `reset-init` этого конфига, в данной последовательности не задействуется, потому что используется `reset halt`, а не `reset init` (хук `reset-init` срабатывает только на `reset init`) — поэтому повторно разгонять/тормозить скорость вручную не требуется. Если в будущем кто-то добавит `reset init` в цепочку и вернётся проблема — сначала проверьте, не ожило ли воздействие этого хука, и при необходимости верните принудительное ограничение скорости (`adapter speed 200` + переопределение хуков `reset-init`/`reset-start`), это уже проверенный fallback.

## ТЕКУЩАЯ ОТЛАДКА: обрыв TCP-связи под нагрузкой (статус на 2026-06-18, не завершено)

**Симптом:** при отправке нескольких сообщений в UART1 модуля (которые форвардятся в TCP) подряд связь стабильно умирает после определённого количества пакетов, требуя ресета. Без аппаратного ресета модуль не виден в сети (ARP не отвечает) с ПК.

### Подтверждённые и исправленные баги (уже в коде, проверено сборкой)

1. **`HardFault_Handler` был "тихим" `while(1)`** (`Core/Src/stm32f4xx_it.c`) — если бы случился реальный HardFault, диагностировать было бы невозможно. Исправлено: теперь печатает `[HARDFAULT] PC=... LR=...` в UART1 перед остановкой (через ассемблерный трамплин + `HardFault_C_Handler`). **На практике HardFault не наблюдался** ни разу — значит, дело не в crash/segfault уровня CPU.

2. **`ethernetif_reset()` добавлена** (`Core/Src/ethernetif.c`) — функция полного пересоздания ETH: `HAL_ETH_Stop_IT` → `HAL_ETH_DeInit` → аппаратный сброс через RCC (`__HAL_RCC_ETHMAC_FORCE_RESET/RELEASE_RESET`, т.к. `HAL_ETH_DeInit` НЕ дёргает линию аппаратного сброса) → `low_level_init()` (полная переинициализация MAC/DMA/PHY заново, включая NRST PHY). Вызывается из `tcp_echo_client.c`/`on_err()` после `ETH_RESET_AFTER_FAILS=3` неудачных попыток подключения подряд (~15 сек). **Подтверждено рабочим**: после такого сброса IP/PHY/ARP восстанавливаются (видно `[lwip] IP: 10.0.1.60` и реально устанавливается TCP-соединение).

3. **`HAL_ETH_Init()`/`DeInit()` не очищают `EthHandle.TxDescList`/`RxDescList`** — проверено по исходникам HAL (`Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_eth.c`), там просто нет кода, который бы их обнулял. Из-за этого счётчик занятых TX-буферов (`BuffersInUse`) копился через рестарт ETH и никогда не возвращался к 0. Исправлено: в `ethernetif_reset()` добавлен явный `memset(&EthHandle.TxDescList, 0, ...)` / `RxDescList`. **Подтверждено в логе**: после фикса `txbuf=0` сразу после `[eth] resetting ETH peripheral`, раньше оставалось зависшим на старом значении.

4. **Double-free pbuf при таймауте передачи** (`low_level_output()` в `ethernetif.c`) — при таймауте `HAL_ETH_Transmit()` (20 мс) HAL сам форсированно очищает бит OWN дескриптора (`heth->ErrorCode |= HAL_ETH_ERROR_TIMEOUT`), и pbuf будет освобождён позже через `HAL_ETH_ReleaseTxPacket()` → `HAL_ETH_TxFreeCallback()`. Старый код ДОПОЛНИТЕЛЬНО делал `pbuf_free(p)` сразу при любой ошибке — двойной free на один pbuf при таймауте, что портит heap lwIP. Исправлено: `pbuf_free(p)` теперь вызывается только если `EthHandle.ErrorCode` НЕ содержит `HAL_ETH_ERROR_TIMEOUT` (т.е. дескриптор не был поставлен в очередь и никто другой его не освободит).

5. **`ETH_TX_DESC_CNT`/`ETH_RX_DESC_CNT` увеличены с 4 (умолчание HAL) до 8** (`Core/Inc/stm32f4xx_hal_conf.h`, override перед `#include "stm32f4xx_hal_eth.h"`) — диагностический шаг, не финальное решение.

6. В `[alive]` heartbeat (`main.c`) добавлено поле `txbuf=%lu` = `EthHandle.TxDescList.BuffersInUse` для прямого наблюдения за утечкой TX-дескрипторов без доп. инструментирования.

### РЕШЕНО (2026-06-18): главная причина найдена и подтверждена инструментацией

Гипотеза из предыдущей версии этого раздела **подтверждена напрямую**: добавлен временный debug-print вокруг `HAL_ETH_ReleaseTxPacket()` (сравнение `BuffersInUse` до/после) и при `tcp_write()==ERR_MEM`. Лог показал:

- `[eth] release stuck: before=N after=N` — печаталось **на КАЖДОМ вызове, начиная с before=1** (то есть с первой же передачи после `[lwip] IP: ...`). `HAL_ETH_ReleaseTxPacket()` не освободил ни одного дескриптора ни разу за весь сеанс (>100 передач).
- `BuffersInUse` рос линейно до 104 и затем заморозился — ровно в этот момент начались `[tcp_echo] tcp_write ERR_MEM (heap exhausted?)`, подряд и постоянно. Это подтверждает: куча lwIP (`MEM_SIZE=16KB`) действительно исчерпывается накопленными pbuf, которые никогда не освобождаются через `HAL_ETH_TxFreeCallback()`.

**Корневая причина:** голова FIFO-очереди дескрипторов (`TxDescList.releaseIndex`, который никогда не сдвигается с 0) застряла с битом OWN навсегда уже на первой передаче — почти наверняка гонка сразу после `HAL_ETH_Start_IT()` в `low_level_init()` (первая передача, скорее всего DHCP DISCOVER, ставится в дескриптор раньше, чем DMA/MAC реально готовы её обслужить). Поскольку `HAL_ETH_ReleaseTxPacket()` устроен строго по FIFO (см. `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_eth.c:1463` — `while (numOfBuf!=0 && pktTxStatus!=0)`, останавливается на первом дескрипторе с установленным OWN), застрявшая голова блокирует освобождение АБСОЛЮТНО ВСЕХ последующих дескрипторов навечно, даже если они реально передались по проводу (а они передавались — ПК получал данные все 60+ секунд, это видно по живому диалогу в логе).

**Фикс (применён, `Core/Src/ethernetif.c`, `low_level_output()`):** если `BuffersInUse > ETH_TX_DESC_CNT` (что само по себе невозможно при корректной работе кольца — прямое доказательство застревания, а не "просто давно не освобождали"), принудительно очищаем застрявший дескриптор-голову той же командой, что использует сам HAL при таймауте (`DESC0 = ETH_DMATXDESC_FS | ETH_DMATXDESC_LS`, это сбрасывает бит OWN), и сразу повторно вызываем `HAL_ETH_ReleaseTxPacket()`, чтобы реально освободить pbuf через `HAL_ETH_TxFreeCallback()`. Временные debug-print (`release stuck`, `tcp_write ERR_MEM`) убраны после подтверждения диагноза — если поведение вернётся, инструментацию легко восстановить (см. git-историю/предыдущую версию этого файла).

**Обновление после первого теста на плате:** гейт `> ETH_TX_DESC_CNT` почти не помог (рост до 50+ продолжался). Заменён на безусловный дренаж: на каждом вызове `low_level_output()` цикл `while (BuffersInUse > 0 && guard-->0) { force-clear головы; HAL_ETH_ReleaseTxPacket(); если без изменений - break; }` (до `ETH_TX_DESC_CNT+1` итераций). **Второй тест:** утечка стала значительно меньше (плато на ~45 вместо 104, и `txbuf=0` после рабочих ресетов), но не до конца ноль во время самого всплеска сообщений — видимо, дренаж не успевает полностью разгрузиться в рамках одного вызова при быстрой серии, и сообщения заканчиваются раньше, чем цикл успевает дойти до 0 (после остановки потока новых вызовов дренаж тоже не может продолжиться, т.к. он только внутри `low_level_output()`). Это уже не критично — TX-утечка больше не доминирующая причина отказа.

### НОВАЯ ОТКРЫТАЯ ПРОБЛЕМА (вскрылась после починки TX-утечки): module не переподключается после `ethernetif_reset()`

После того как TX-утечка перестала маскировать остальные эффекты, проявился **отдельный** баг: после нескольких циклов `ethernetif_reset()` модуль входит в устойчивый цикл "сброс → `[lwip] IP: ...` → мгновенный `connection error` → через 3 попытки снова сброс", **навсегда**, без единого успешного `[tcp_echo] connected`. При этом `txbuf=0` (утечки дескрипторов больше нет), `eth=LINK_UP` после первого тика — то есть PHY физически поднимается, но TCP не устанавливается.

Важное наблюдение пользователя: ARP-таблица ПК **показывает корректную запись** для модуля (`10.0.1.60 → 02-00-00-00-00-01, dynamic`) даже во время этого зависания — то есть на уровне Ethernet/ARP всё видно нормально, проблема глубже (похоже на TCP handshake или RX-путь модуля).

Аналогия с уже найденным TX-багом: возможно, есть **симметричный баг на RX-стороне** — `g_eth_rx_alloc_status` (бывший `RxAllocStatus`, см. `ethernetif.c`) может зависать в `RX_ALLOC_ERROR` после нескольких циклов сброса, из-за чего `low_level_input()` перестаёт вызывать `HAL_ETH_ReadData()` вообще (гейт `if (RxAllocStatus == RX_ALLOC_OK)`) — тогда модуль продолжает отправлять SYN (PC видит и ARPит его), но никогда не обрабатывает входящий SYN-ACK.

**Применены два фикса для проверки (собраны, НЕ ПРОВЕРЕНЫ на плате):**
1. `ethernetif_reset()` теперь дополнительно вызывает `etharp_cleanup_netif(netif)` — очищает ARP-таблицу lwIP (программное состояние, не аппаратное; наш сброс трогал только периферию ETH, а ARP-кэш lwIP мог оставаться "грязным" между циклами — это согласуется с давним наблюдением пользователя "помогает только сброс по питанию", т.к. питание пересоздаёт весь lwIP с нуля через `lwip_init()`, а наш софт-ресет — нет).
2. `RxAllocStatus` → переименован в публичный `g_eth_rx_alloc_status` (`ethernetif.h`), добавлен в heartbeat: `[alive] ... rxalloc=N` (main.c). `0` = `RX_ALLOC_OK`, `1` = `RX_ALLOC_ERROR`. Если в следующем тесте `rxalloc=1` будет видно во время зависания — это подтвердит гипотезу про исчерпание RX_POOL.

**Результат теста:** `rxalloc=0` все 100% времени, включая момент постоянного зависания — гипотеза про истощение RX_POOL **отклонена**. `etharp_cleanup_netif()` тоже не помог — цикл "сброс → мгновенный connection error" продолжился без изменений.

**Новая улика:** после сброса `[tcp_echo] connection error, will retry` появляется **мгновенно**, без обычной 5-секундной паузы нашего собственного таймера подключения. Это означает, что это НЕ наш `tcp_abort()`-по-таймауту (который быждал `RECONNECT_INTERVAL_MS`), а настоящий немедленный RST из сети. Рабочая гипотеза: коммутатор/роутер видит частые down/up на порту модуля (каждый `ethernetif_reset()` дёргает линк) и включает защиту от "флаппинга" порта — временно блокирует/игнорирует порт после нескольких быстрых переключений состояния линка за короткое время. То есть **наши собственные частые сбросы ETH могут быть причиной того, что сеть не восстанавливается**, а не лечением.

**Применённый фикс (собран, НЕ ПРОВЕРЕН):** экспоненциальный backoff между `ethernetif_reset()` (`tcp_echo_client.c`): `s_reset_count` считает подряд идущие сбросы без единого успешного подключения; задержка перед следующей попыткой подключения после сброса = `RECONNECT_INTERVAL_MS << min(s_reset_count, 4)`, то есть 5с → 10с → 20с → 40с → 60с (потолок `ETH_RESET_BACKOFF_CAP_MS`). Сбрасывается в 0 при любом успешном `[tcp_echo] connected`. В лог добавлено сообщение `[tcp_echo] backoff Nms before next try`.

**Найден баг в самом backoff-фиксе (тест показал):** в логе сообщение "backoff 40000ms before next try" печаталось, но реальная пауза перед следующим сбросом была всего ~10 секунд — backoff не действовал. Причина: в `tcp_echo_client_poll()`, `case ECHO_STATE_CONNECTING` (таймаут SYN без ответа), код вызывал `tcp_abort(s_pcb)` (это синхронно вызывает `on_err()`, который сам корректно вызывает `reset_to_idle()` и при необходимости выставляет backoff), а СРАЗУ ПОСЛЕ — ещё раз unconditionally вызывал `reset_to_idle()`, которая просто заново выставляла `s_next_action_tick = HAL_GetTick() + RECONNECT_INTERVAL_MS` (5с), затирая backoff. **Исправлено**: теперь при `s_pcb != NULL` `reset_to_idle()` вызывается только один раз (внутри `on_err()`, через цепочку `tcp_abort`), без повторного затирания снаружи. Собрано, **ЕЩЁ НЕ ПРОВЕРЕНО на плате**.

**Тест на другом порту роутера (2026-06-18): проблема повторилась идентично.** Это ИСКЛЮЧАЕТ теорию про flap-protection свича — проблема не во внешней сети, она в модуле. При этом `txbuf` снова вырос до ~50-53 несмотря на фикс дренажа дескрипторов (фикс не дал измеримого эффекта на пик — осталось почти так же, как без него, просто без фикса было 104, с фиксом ~50-53; ещё предстоит понять, почему дренаж не справляется полностью).

**Ключевое совпадение, объясняющее ВСЁ:** порог зависания (~50-53 пакетов) **не зависит от паузы между пакетами и не зависит от порта свитча** — то есть зависит только от КОЛИЧЕСТВА переданных пакетов, не от времени и не от внешней сети. При `MEM_SIZE=16KB` и примерной накладной стоимости ~300 байт на pbuf (текст ~70-90 байт + служебные данные lwIP), `16384/300 ≈ 54` — это совпадает с порогом практически точно. Это означает: лежащая в основе TX-утечка (pbuf, висящий с лишней ссылкой из-за `HAL_ETH_ReleaseTxPacket()`) всё ещё исчерпывает кучу lwIP `MEM_SIZE`, и именно ЭТА куча — программное состояние lwIP, а не аппаратная часть ETH — никогда не восстанавливалась нашим `ethernetif_reset()` (он трогает только MAC/DMA/PHY + ARP-таблицу, но не `mem_init()`/`memp_init()`). Это объясняет давнее наблюдение пользователя "помогает только сброс по питанию" — питание это единственное, что раньше пересоздавало кучу lwIP с нуля.

**Применённый фикс (собран, ЕЩЁ НЕ ПРОВЕРЕН):** `ethernetif_reset()` теперь дополнительно вызывает `dhcp_stop(netif)` + `mem_init()` + `memp_init()` — полный сброс кучи lwIP (`MEM_SIZE`) и всех стандартных memp-пулов (TCP_PCB, TCP_SEG, PBUF, UDP_PCB и т.д.), той самой памяти, которую раньше реально пересоздавал только физический сброс питания. Безопасно вызывать в этой точке, так как `TxDescList`/`RxDescList` уже обнулены ВЫШЕ в той же функции — никто больше не должен ссылаться на старую кучу. `RX_POOL` (кастомный пул через `LWIP_MEMPOOL_DECLARE`) отдельный от стандартных memp-пулов и не трогается этим вызовом — он уже переинициализируется внутри `low_level_init()`.

**Тест показал первый РЕАЛЬНЫЙ HardFault за всю сессию** (наша диагностика наконец сработала!): `[HARDFAULT] PC=0x08007464 LR=0x00000000 ...` сразу после `[eth] HAL_ETH_Init OK` при аварийном `ethernetif_reset()`. По `.map`-файлу (`arm-none-eabi-addr2line`/`nm --numeric-sort`) PC попал точно в `low_level_output()` (`ethernetif.c`).

**Причина — баг в МОЁМ собственном предыдущем фиксе:** `dhcp_stop(netif)` останавливает DHCP-клиент, но НЕ освобождает структуру `struct dhcp`, которую `dhcp_start()` выделил через `mem_malloc()` ещё при загрузке — `netif->dhcp` продолжает на неё указывать. Сразу после этого `mem_init()` сбрасывает free-list ВСЕЙ кучи — та же память может быть выдана повторно под что-то другое, пока `netif->dhcp` всё ещё "висит" на ней. Первая же новая аллокация (DHCP/ARP-пакет после ресета) переписала эту память, и тогда что-то внутри DHCP-обработки (или просто следующий `low_level_output()`, работающий с уже мусорным pbuf) обратилось к испорченным данным → HardFault.

**Исправлено:** перед `mem_init()` добавлен `dhcp_cleanup(netif)` (реально делает `mem_free()` структуры и очищает client-data слот netif — нашёл в `Middlewares/Third_Party/LwIP/src/core/ipv4/dhcp.c:712`). Также добавлен `dhcp_start(netif)` после `low_level_init()` — закрывает отдельный, ранее не замеченный гэп: ни `ethernetif_reset()`, ни `low_level_init()` сами по себе никогда не перезапускали DHCP-клиента после сброса (это делают только `MX_LWIP_Init()` при загрузке и `ethernetif_poll_link()` при переходе линка из down в up) — то есть после каждого нашего софт-ресета модуль работал на старом IP без активной DHCP-аренды вообще.

Собрано, **ЕЩЁ НЕ ПРОВЕРЕНО на плате**.

**ПОДТВЕРЖДЕНО ТЕСТОМ (2026-06-18): главная цель достигнута.** HardFault не повторился. Модуль теперь **дважды за один сеанс сам восстановился** после аварийного `ethernetif_reset()` (`[tcp_echo] connected` после `backoff 5000ms` — впервые за всю сессию отладки!). Цикл стал самовосстанавливающимся: работает ~85-100 сек (пока `txbuf` растёт до ~50-53 и куча lwIP не исчерпывается) → связь рвётся → аварийный сброс (теперь со сбросом `mem_init()`/`memp_init()`/DHCP) → успешное переподключение. Раньше после первого разрыва модуль навсегда зависал без физического ресета — это и было главной проблемой пользователя, и она решена.

**Что осталось не идеальным (не блокирует работу, но стоит доделать при следующем заходе):** утечка TX-дескрипторов (`HAL_ETH_ReleaseTxPacket()`, см. выше) всё ещё не устранена до конца — `txbuf` всё равно доходит до ~50-53 при активном обмене вместо удержания около 0, из-за чего связь периодически обрывается и требует аварийного сброса. Теперь это не катастрофа (само восстанавливается), но было бы лучше не доходить до этого вовсе. Следующий шаг при желании докопаться: добавить точечную диагностику внутри цикла дренажа в `low_level_output()` (`ethernetif.c`) — почему он не успевает полностью разгрузить кольцо дескрипторов во время быстрой серии пакетов.

### Параллельно найденный (не связанный) баг: индикатор LED2/GREEN не горит

Пин LAN8720 pad2 (`nINTSEL`/`LED2`) после ресета PHY переключается в режим индикатора LED2, но постоянный pull-down 1кОм (см. секцию про REFCLKO-фикс выше, аппаратная правка платы) держит линию прижатой к GND и мешает PHY управлять ей. GREEN светится ~1 сек сразу после ресета (артефакт момента сброса strap), потом гаснет. **Это не связано с сетевой проблемой** — LED2 не участвует в линиях данных RMII. Можно игнорировать или отпаять резистор и придумать схему, которая держит pull-down только во время сброса (например, RC-цепочка вместо чистого резистора).

### ОКОНЧАТЕЛЬНЫЙ ФИКС TX-утечки дескрипторов (2026-06-18)

Пользователь настоял на полном устранении утечки (не только самовосстановлении): "конечно устранить! этот дефект является одним из важнейших".

**Точная диагностика (новая verbose-инструментация дренажа в `low_level_output()`):** на КАЖДОМ вызове, всю сессию, лог показывал `idx=0 hadPkt=0 desc0=0x30D00000 before=N after=N` — то есть `releaseIndex` навсегда застыл на 0, слот 0 пуст (`PacketAddress[0]==NULL`), а `BuffersInUse` (`before`) тем не менее растёт от реальных передач через другие слоты кольца. Дренаж не делал ни одной успешной итерации НИКОГДА.

**Найден точный баг в самом HAL (`Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_eth.c:1451-1535`, `HAL_ETH_ReleaseTxPacket()`):** функция идёт по кольцу начиная с `releaseIndex`, до `BuffersInUse` итераций, ПРОПУСКАЯ пустые слоты (`PacketAddress[idx]==NULL`) только ЛОКАЛЬНО (`idx++` в переменной на стеке) — `dmatxdesclist->releaseIndex` и `dmatxdesclist->BuffersInUse` обновляются ТОЛЬКО внутри ветки успеха (когда находит слот с `PacketAddress!=NULL && OWN==0`, строки 1519-1525). Если по пути встречается хоть один слот с `OWN` ещё установленным — функция немедленно прерывается (`pktTxStatus=0`) и ВЕСЬ локальный прогресс (включая уже пройденные NULL-пропуски) отбрасывается, ничего не коммитится назад в handle. Дальше та же ситуация повторяется на каждом следующем вызове — `releaseIndex` навечно замирает.

Отдельно: `ETH_Prepare_Tx_Descriptors()` (строка 3137-3141) отказывается повторно использовать слот кольца, если `PacketAddress[idx] != NULL` — **даже если `OWN` уже снят** (пакет реально ушёл в сеть). Единственный штатный механизм очистки `PacketAddress[]` — сломанный `HAL_ETH_ReleaseTxPacket()` выше. Итог: слоты с уже переданными пакетами навсегда остаются "занятыми" программно → `BuffersInUse` только растёт → каждый такой pbuf держит лишнюю ссылку (`pbuf_ref()` в `low_level_output()`) → куча lwIP (`MEM_SIZE`=16KB) исчерпывается через ~50-54 пакета (совпадает с прошлым расчётом `16384/300≈54`).

**Фикс (применён, см. `Core/Src/ethernetif.c`):** перестали доверять бухгалтерии HAL вообще. Старый verbose drain-loop в `low_level_output()` заменён на новую функцию `eth_tx_drain_all()`, которая каждый вызов обходит ВСЕ `ETH_TX_DESC_CNT` физических слотов кольца напрямую (не используя `releaseIndex`/`HAL_ETH_ReleaseTxPacket()`): если `PacketAddress[idx]!=NULL && OWN==0` — слот реально готов, вызывается `HAL_ETH_TxFreeCallback()` (= `pbuf_free()`) и `PacketAddress[idx]` обнуляется; иначе слот считается ещё занятым. После обхода `BuffersInUse` и `releaseIndex` пересчитываются с нуля из реального состояния кольца. Это устраняет саму возможность "застревания" — больше нет общего `releaseIndex`, который можно заклинить, и `PacketAddress[]` всегда отражает реальное состояние, так что `ETH_Prepare_Tx_Descriptors()` больше никогда не откажет на основании устаревшей записи.

Собрано, билд проходит (`cmake --build build`), **ещё не проверено на плате** — следующий шаг: прошить и прогнать длительный тест (как раньше, burst трафика на протяжении нескольких минут), убедиться что heartbeat-поле `txbuf=` теперь держится около 0-1 постоянно (а не растёт до 50+), и что `ethernetif_reset()`/backoff-цикл больше не требуется вовсе.

**ПОДТВЕРЖДЕНО ТЕСТОМ (2026-06-18): TX-утечка дескрипторов устранена.** `txbuf=1` держался стабильно весь 270-секундный прогон (раньше к 50-53 пакету уходил в рост и связь рвалась). `eth_tx_drain_all()` работает как задумано — фикс TX-утечки закрыт, можно больше не возвращаться к этой части.

### Новый, отдельный баг: TCP-клиент замолкает навсегда после одного `connection error`

После исправления TX-утечки нашёлся СЛЕДУЮЩИЙ дефект, ранее маскировавшийся постоянными зависаниями ETH. Симптом: один раз проходит `[tcp_echo] connection error, will retry`, после чего — полная тишина в TCP-логике на 220+ секунд (никаких "connected"/"connection error"), хотя `[alive]` heartbeat продолжает идти каждые 5 сек и `arp -a` подтверждает, что модуль виден в сети. **Значит зависла не прошивка и не ETH/IP-стек, а конкретно state-машина в `tcp_echo_client.c`.**

Найдены два места в `start_connect()` (`tcp_echo_client.c`), которые при ошибке молча уходили в `reset_to_idle()` без единого сообщения в лог: `tcp_new() == NULL` (исчерпан `MEMP_NUM_TCP_PCB`, в `lwipopts.h` всего `4`) и `tcp_connect() != ERR_OK`. Если стейт-машина попадает в один из этих путей, она будет повторять попытку каждые 5 сек молча, бесконечно — внешне выглядит как полное зависание, хотя на самом деле просто крутится вхолостую без единого вывода.

**Фикс (применён):** добавлены `rx_push()` с текстом ошибки в оба этих места (`tcp_new() failed (PCB pool exhausted?)` и `tcp_connect() failed err=N`). Также добавлена однобуквенная диагностика состояния `tcp_echo_client_state_char()` (`'I'`=idle, `'C'`=connecting, `'E'`=connected/established), выведенная в heartbeat как новое поле `tcp=` (`main.c`): `[alive] t=... eth=... txbuf=... rxalloc=... tcp=I/C/E`.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, повторить тест до момента "зависания", прочитать `tcp=` в heartbeat (покажет, застряла машина в `C` (CONNECTING — SYN ушёл, ответа нет) или крутится в `I` (IDLE — `start_connect()` падает на одном из двух теперь залогированных путей)), и/или дождаться появления нового сообщения `tcp_new() failed` / `tcp_connect() failed err=N` в логе.

**ПОДТВЕРЖДЕНО ТЕСТОМ (2026-06-18): `tcp_connect() failed err=-1` = `ERR_MEM`.** Лог дал точные числа: `heap=16312/16384 tcp_pcb=1/4 tcp_seg=0/16 pbuf=0/8` (формат `used/avail`). Пулы `TCP_PCB`/`TCP_SEG`/`PBUF_POOL` практически пустые — значит утечка не в счётчиках сегментов/PCB, а в самой куче lwIP (`MEM_SIZE`=16KB, `mem_malloc()`), которая была занята на 16312 из 16384 байт (свободно всего 72 байта).

### Второй, отдельный баг: утечка кучи lwIP в `tcp_write()` (не связан с TX-дескрипторами)

Добавил поле `heap=used/avail` в heartbeat (`main.c`, через `lwip_stats.mem`) — это показало рост в реальном времени, не только в момент сбоя. **Результат теста:** куча росла **с каждым отправленным сообщением** во время активного обмена (`1476→1856→5472→16056→16264→16344` за ~30 сек активной переписки), затем **переставала расти** ровно когда переставали печатать, и **не падала** даже после 20+ секунд полного простоя без нового трафика — то есть это настоящая утечка (не задержка ACK), и она привязана к каждой передаче через `tcp_write()`, а не к разрыву соединения.

**Причина:** `TCP_OVERSIZE` в lwIP по умолчанию равен `TCP_MSS` (1460 байт) — каждый `tcp_write()`, который начинает новый "хвостовой" непосланный сегмент, резервирует в куче этот запас, чтобы последующие мелкие записи могли дописываться в тот же сегмент без новой аллокации. В `tx_flush()` (`tcp_echo_client.c`) после каждого `tcp_write()` сразу вызывается `tcp_output()` — то есть каждое сообщение становится отдельным "хвостом" с собственным резервом ~1460 байт, который не переиспользуется следующей записью (это уже новый сегмент). Магнитуда роста (~1400-1500 байт на сообщение) точно совпала с `TCP_MSS`, подтвердив диагноз.

**Фикс (применён, `Core/Inc/lwipopts.h`):** `#define TCP_OVERSIZE 0` — официально поддерживаемое значение (см. комментарий в `lwip/opt.h`: "0: Don't oversize, always allocate the exact size"), отключает резервирование запаса полностью; `tcp_pbuf_prealloc()` будет выделять ровно нужный размер на каждую запись. Для нашего паттерна использования (всегда `tcp_output()` сразу после `tcp_write()`) это не теряет производительность, так как мы и не пользовались переиспользованием запаса.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, повторить тот же тест (несколько сообщений через UART подряд), убедиться что `heap=` в heartbeat теперь держится стабильно низко (не растёт пропорционально количеству сообщений), и что `tcp_connect()` больше не падает с `ERR_MEM` после/во время длительного обмена.

**ТЕСТ (2026-06-18): `TCP_OVERSIZE=0` уменьшил рост кучи (~1400→~150-250 байт/сообщение), но НЕ устранил его.** Куча всё равно дошла до предела (`16384/16384`) за ~75 сек активного обмена и `tcp_connect()` снова упал с `ERR_MEM`. Значит `TCP_OVERSIZE` был не единственной причиной — есть утечка и в самих данных (не только в запасе под них). Также замечена аномалия: после одного `ethernetif_reset()` heap показал `17596/16384` — **больше объявленного объёма** (возможна порча счётчиков статистики или реальное повреждение памяти при сбросе, требует отдельной проверки).

**Новая диагностика (применена):** `tcp_echo_client_sndqueuelen()` (`tcp_echo_client.c`/`.h`) возвращает `tcp_sndqueuelen(s_pcb)` — число pbuf в очереди отправки PCB (`unsent`+`unacked`). Добавлено в heartbeat как `sndq=` (`main.c`). Если это число растёт без остановки во время активного обмена (а соединение при этом продолжает работать) — значит ACK не освобождает отправленные данные, и утечка именно здесь, а не в "запасе" `TCP_OVERSIZE` и не в RX-пути.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, повторить тест, прислать лог с новым полем `sndq=` в heartbeat.

**Найден отдельный баг диагностики (2026-06-18): счётчик `lwip_stats.mem.used` не сбрасывается при `ethernetif_reset()`.** В длинном тесте (t=480-505 сек, уже после нескольких циклов аварийного сброса) heap показал `38492/16384` — **больше объявленного объёма кучи**, при этом соединение продолжало работать (`tcp=E`, без `ERR_MEM`). Проверка `mem_init()` (`Middlewares/Third_Party/LwIP/src/core/mem.c:516`) показала: эта функция сбрасывает РЕАЛЬНЫЙ список свободных блоков аллокатора (поэтому настоящая куча действительно очищается, и работа после сброса продолжается нормально), но НЕ трогает `lwip_stats.mem.used` — это отдельная переменная статистики, обновляемая только инкрементами/декрементами при каждом malloc/free. После каждого `ethernetif_reset()` она просто продолжает копиться от старого значения, так что через несколько циклов сброса показывает фантастические числа, не отражающие реальное состояние кучи.

**Фикс (применён, `ethernetif_reset()` в `ethernetif.c`):** после `mem_init()`/`memp_init()` добавлен `memset(&lwip_stats.mem, 0, sizeof(lwip_stats.mem))` + `MEM_STATS_AVAIL(avail, MEM_SIZE)` — обнуляет счётчик статистики синхронно с реальным сбросом кучи. Это никак не влияет на сам факт утечки (она в реальном аллокаторе, не в счётчике) — это чисто чинит достоверность диагностики `heap=` в heartbeat после сброса.

**Важно: подлинность утечки в ПЕРВОМ цикле (до первого сброса) остаётся подтверждённой** — там `heap=16384/16384` совпало с настоящим падением `tcp_connect()` с `ERR_MEM` (это не могло быть просто артефактом счётчика, так как `ERR_MEM` возвращается реальным `mem_malloc()`, не основанным на статистике). Утечка реальна, просто после починки счётчика её будет проще отслеживать дальше.

Собрано, билд проходит, **ещё не проверено на плате** — нужно повторить тест с самого начала (после прошивки) и прислать ПЕРВЫЕ ~100 сек лога (до первого `ethernetif_reset()`), с полем `sndq=`, чтобы увидеть, растёт ли очередь отправки PCB в момент настоящей утечки.

**Результат теста: `sndq=0` всё время** (даже в момент `ERR_MEM`) — утечка не в очереди PCB. **Куча росла даже без единого набранного сообщения** (t=5000→105000, до первого "Hello Module" в логе) — рост шёл от автоматических `ping #N`, которые `tcp_echo_client_poll()` сам шлёт каждые `SEND_INTERVAL_MS`=2000 в состоянии CONNECTED. TCP keepalive здесь не виноват: он сбрасывается каждой передачей, а пинг идёт чаще интервала keepalive, так что последний физически не успевает сработать.

**Точная диагностика (добавлена в `low_level_output()`):** вывод `p->ref` пакета ПЕРЕД нашим `pbuf_ref()` — показал `ref=1` стабильно на каждом пакете (ожидаемое поведение, лишней ссылки до нас нет). Затем добавлена диагностика прямо в `eth_tx_drain_all()`: печать при каждом реальном освобождении слота. **За весь тест (~90+ передач) — НИ ОДНОЙ строки освобождения.** Значит `eth_tx_drain_all()` никогда ничего не находит для очистки, хотя `txbuf` (`BuffersInUse`) стабильно показывал `1`.

### НАЙДЕН ИСТИННЫЙ КОРЕНЬ ОБЕИХ УТЕЧЕК (TX-дескрипторов и кучи lwIP)

Прямая проверка источника `stm32f4xx_hal_eth.c` показала: `heth->TxDescList.CurrentPacketAddress` (то самое поле, которое `ETH_Prepare_Tx_Descriptors()` копирует в `PacketAddress[descidx]`, строка 3259) **устанавливается только внутри `HAL_ETH_Transmit_IT()`** (режим прерываний, строка 1048: `heth->TxDescList.CurrentPacketAddress = (uint32_t *)pTxConfig->pData;`). В `HAL_ETH_Transmit()` — **polling-режиме, который мы используем** (строки 962-1028) — это поле НИГДЕ не устанавливается!

Это означает: всё время, что мы вызывали `HAL_ETH_Transmit()`, `PacketAddress[]` никогда не получал указатель на реальный переданный pbuf — там всегда оставался NULL/устаревшее значение. Отсюда следует ВСЁ:
- `HAL_ETH_ReleaseTxPacket()` (старая HAL-функция) всегда видела `PacketAddress[idx]==NULL` и просто "пропускала" каждую запись — отсюда и самый первый баг сессии (рост `BuffersInUse` до 50-104 и обрыв связи).
- Наша замена `eth_tx_drain_all()` страдала ТЕМ ЖЕ корнем — она тоже ищет `PacketAddress[idx]!=NULL`, и тоже никогда не находила, поэтому ни разу не вызвала `pbuf_free()` для лишней ссылки, взятой нашим `pbuf_ref(p)`.
- Каждый переданный пакет навсегда оставлял ОДНУ лишнюю ссылку (`pbuf_ref()` без последующего `pbuf_free()`), которую lwIP сам никогда не отпускал, потому что эту ссылку добавляли МЫ, а не lwIP — и это и есть утечка кучи `MEM_SIZE`, которую гонялись всю сессию.

**Фикс (применён, `low_level_output()` в `ethernetif.c`):** перед вызовом `HAL_ETH_Transmit()` добавлена строка `EthHandle.TxDescList.CurrentPacketAddress = (uint32_t *)p;` — то же самое, что делает `HAL_ETH_Transmit_IT()` для режима прерываний. Теперь `ETH_Prepare_Tx_Descriptors()` корректно сохраняет реальный указатель в `PacketAddress[]`, и `eth_tx_drain_all()` сможет находить и освобождать его как положено.

Вся verbose-диагностика (`[eth] tx ...`, `[eth] drain free ...`) убрана из `low_level_output()`/`eth_tx_drain_all()` после нахождения причины — она была временной. `heap=`/`tcp=` в heartbeat (`main.c`) оставлены как полезные постоянные диагностические поля.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, прогнать длинный тест с активным обменом (как раньше), убедиться что `heap=` в heartbeat теперь держится стабильно низко неограниченно долго, `tcp_connect()` больше не падает с `ERR_MEM`, и аварийный `ethernetif_reset()`/backoff не требуется вовсе.

### ПОДТВЕРЖДЕНО: TX/heap-утечка устранена окончательно — НО найден новый баг: потеря IP без восстановления (2026-06-18, после ~2 часов наработки)

После фикса `CurrentPacketAddress` модуль проработал часами без роста кучи: `heap=128/16384` стабильно от t=7575000ms до t=8090000ms (больше 2 часов, замер до и после) — TX/heap-утечка закрыта окончательно, к этой части возвращаться не нужно.

**Новый, отдельный баг:** в это же время `tcp=I` (idle) без единого сообщения об ошибке, и модуль полностью пропал из сети — `arp -a` (полный, без фильтра) не показывает НИ ОДНОГО неизвестного адреса в подсети 10.0.1.x, только роутер/инфраструктуру/мультикаст. Модуль не отвечает ни под каким IP.

**Причина (подтверждена чтением исходников lwIP, `Middlewares/Third_Party/LwIP/src/core/ipv4/dhcp.c`):** при истечении DHCP-аренды (`dhcp_coarse_tmr()` → `t0_timeout` → `dhcp_release_and_stop()`, строка 1371) lwIP сам обнуляет IP интерфейса: `netif_set_addr(netif, IP4_ADDR_ANY4, ...)`, затем вызывает `dhcp_start()` для получения новой аренды. Это штатное поведение lwIP. НО: пока IP равен `0.0.0.0`, `main.c:133` (`if (netif_is_up(&gnetif) && !ip4_addr_isany_val(...)) { tcp_echo_client_poll(); }`) полностью пропускает вызов `tcp_echo_client_poll()` — а это значит, что наш ЕДИНСТВЕННЫЙ механизм самовосстановления (`ethernetif_reset()` после 3 неудачных TCP-подключений, `tcp_echo_client.c`) даже не успевает сработать, потому что вся его логика живёт внутри `tcp_echo_client_poll()`! Если DHCP не может сам переполучить аренду (по любой причине — таймаут ответа от роутера, потерянный broadcast и т.д.) — **нет вообще никакого механизма восстановления**. Здоровая сеть отвечает на DHCP DISCOVER за доли секунды; зависание на час+ означает, что DHCP-клиент lwIP застрял сам, и ничего извне его не подталкивает.

**Фикс (применён, `main.c`, основной `while(1)` цикл):** добавлен независимый от TCP watchdog. Считается время, прошедшее с момента, когда IP пропал (`ip_missing_since`, статическая переменная). Если IP отсутствует дольше `DHCP_STUCK_TIMEOUT_MS` = 90000 (90 сек — намного больше, чем нужно здоровой сети для DHCP) — вызывается тот же `ethernetif_reset(&gnetif)`, что и при зависании TCP (полный сброс ETH MAC/DMA/PHY + куча lwIP + перезапуск DHCP), независимо от состояния `tcp_echo_client_poll()`. Лог: `[lwip] no IP for too long, forcing ETH reset`.

Собрано, билд проходит, **ещё не проверено на плате** — следующий шаг: прошить, либо дождаться следующего естественного истечения DHCP-аренды (часы), либо для быстрой проверки временно уменьшить `DHCP_STUCK_TIMEOUT_MS` до маленького значения (например 10000) и принудительно вызвать `dhcp_release_and_stop()`/имитировать потерю IP, убедиться что `[lwip] no IP for too long, forcing ETH reset` появляется в логе и модуль восстанавливает IP/связь сам, без участия пользователя.
